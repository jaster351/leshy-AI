# Леший: только первоначальный вход в глобальный рой

`bootstrap.json` — **статический справочник первоначальных HTTPS-узлов**.
Его назначение — помочь новой установке найти участников сети.
Это **не** реестр всех пользователей и **не** база знаний.

Схема:

```json
{
  "schema_version": 1,
  "network_id": "leshy-public-v1",
  "seeds": [
    {"id": "seed-1", "url": "https://реальный-адрес-узла"}
  ]
}
```

Адрес в примере вымышленный. В опубликованном каталоге список пока **пуст**,
поскольку доступных из интернета и проверенных серверов ещё нет. Пока
оператор сети не развернёт хотя бы один seed, состояние клиентского
Лешего будет `waiting_for_seeds` и **глобальное подключение не состоится**.

## Что хранится здесь

Только публичные, относительно стабильные **адреса входа** и версия схемы.
Список меняется владельцем репозитория редко: при добавлении или
удалении основных узлов.

**Никаких** пулов оперативной памяти, данных моделей, истории диалогов,
вопросов, результатов инференса, статусов обычных пользователей, их
IP-адресов, аккаунтов, списков подключённых компьютеров, приватных ключей
и общего журнала знаний в GitHub быть не должно.

## Что происходит на клиенте

1. При включённом auto-join (по умолчанию) Леший загружает
   `bootstrap.json` через HTTPS и проверяет строгую схему.
2. Список адресов сохраняется локально в
   `LeshyBrain/cluster/bootstrap-directory.json`.
3. Следующее подключение и повторная регистрация идут **на seed напрямую**.
   При успешной работе seed обращения к GitHub не нужны.
4. Если все известные seed недоступны, Леший может заново перечитать
   GitHub-каталог, но не чаще одного раза в 15 минут.
5. Если GitHub недоступен, уже сохранённые seed остаются доступными.
   Если сам рой недоступен, локальная LLM продолжает работать.

Текущая регистрация по HTTPS — **не реальный P2P**. Для полноценного
роя понадобится обмен адресами между участниками (например, подписанные
gossip/DHT-сообщения), NAT traversal/relay и защищённый транспорт задач.
После их реализации GitHub не будет участвовать в распределении задач
или синхронизации знаний.

В версии 1.10.95 начат обмен прямыми адресами: обычные узлы могут получать
от добровольного публичного HTTPS-узла подписанные им объявления о
собственной доступности (только адрес и идентификатор), хранить их локально
и использовать вместо GitHub при отказе начального адреса. Это пока
ограниченная адресная книга, а не полнофункциональные DHT/gossip,
NAT traversal или безопасное распределённое исполнение.
Подробности: docs/SWARM_PEER_EXCHANGE_1.10.95.md.

## Где сохранять остальную информацию

- **Проверенные общие знания:** реплицируемое версионированное хранилище
  между узлами, подписанные изменения, Merkle-хеши, догоняющая
  синхронизация и защита от конфликтов.
- **Объявления о доступности узлов:** краткоживущие записи на узлах роя
  (TTL), без коммитов в GitHub.
- **Задания и ответы:** на согласованных вычислительных узлах, с
  изоляцией владельцев и удалением после срока хранения.
- **Секреты, переписки, личная память:** не попадают в глобальный рой без
  отдельного осознанного разрешения.

Реальный внешний seed должен использовать TLS, защищённую регистрацию,
лимиты и мониторинг. Для вычислительного участия понадобится отдельное
разрешение пользователя, а не только auto-join.

См. `docs/GITHUB_BOOTSTRAP_SWARM_1.10.94.md`.


## Каноническая точка входа: GitHub

**Единственный штатный источник первоначального обнаружения глобального роя:**

`https://raw.githubusercontent.com/jaster351/leshy-AI/main/swarm/bootstrap.json`

Человекочитаемая страница:
`https://github.com/jaster351/leshy-AI/blob/main/swarm/bootstrap.json`

Этот адрес уже жёстко задан в `src/leshy/swarm_bootstrap.py` как `GITHUB_MANIFEST_URL`. Пользователю не нужно вручную вписывать GitHub в конфигурацию. Клиент скачивает JSON, проверяет точную схему и затем использует адреса реально работающих seed-узлов. **GitHub — вход в каталог, а не сервер регистрации или исполнитель задач.** Регистрация направляется на сервер из `seeds` по `POST /v1/swarm/hello`.

### Поля рабочего `bootstrap.json`

- `schema_version` = `1`: текущий обязательный формат каталога.
- `network_id` = `leshy-public-v1`: идентификатор официального публичного роя.
- `seeds` = массив из 0–16 записей `{"id":"узел","url":"https://настоящий-доступный-домен"}`. Адрес должен указывать на действующий HTTPS-сервер, обслуживающий протокол регистрации. Здесь **не** должен стоять URL GitHub: GitHub не принимает `POST /v1/swarm/hello` за Лешего.
- Иных полей в опубликованном JSON быть не должно: текущая проверка схемы их отклонит.

**Почему `seeds: []` сейчас пусто:** в репозитории нет подтверждённого доступного извне HTTPS-сервера регистрации. Указывать несуществующий домен, случайный IP, localhost или raw.githubusercontent.com как seed было бы ошибкой. Это не недописанное значение, а признак неразвёрнутой публичной сети. Пока не будет настоящего seed, клиент обязан показывать `waiting_for_seeds`, а не заявлять об успешном вступлении.

### Что необходимо для заполнения `seeds` и запуска

1. Развернуть хотя бы один публично доступный HTTPS rendezvous-сервер Лешего под контролем оператора и проверить его регистрацию `POST /v1/swarm/hello` с корректной подписью.
2. Настроить TLS, ограничение частоты, журналирование без секретов, защиту регистрации и мониторинг работоспособности.
3. Только после подтверждения работы записать `id` и реальный `url` этого сервера в `swarm/bootstrap.json`.
4. Клиент получает обновлённый каталог через GitHub, сохраняет его локально и обращается напрямую к seed. Сетевая регистрация сама по себе **не** означает готовых распределённых вычислений или обмена приватными данными.

### Проверка текущего статуса

```powershell
Invoke-RestMethod 'http://127.0.0.1:8765/v1/swarm/status' | ConvertTo-Json -Depth 5
```

Обращайте внимание на `github_directory_url`, `seed_count`, `bootstrap_source`, `state`, `last_error`, `global_mesh_connected`. При `seeds: []` ожидаются `seed_count: 0` и `state: waiting_for_seeds`. Это не баг маршрутизации GitHub; это отсутствие опубликованного начального сервера.

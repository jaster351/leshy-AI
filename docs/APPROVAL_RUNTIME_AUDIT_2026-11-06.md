# Аудит фактической границы Human Approval (2026-11-06)

Основание: `main` @ `d47bedb3ce570cfc58984a590cf1508542c71cfd`. Это **статический аудит**, не доказательство эксплуатации через HTTP и не E2E-проверка.

## Подтверждённый разрыв

В `src/leshy/browser_agent.py` метод `BrowserAgent.execute(action, *, approved=False)` при любом истинном `approved` выставляет `_approval_verified=True` для действий `MUTATE/COMMIT/FINANCIAL`. Он не принимает и не проверяет owner UUID, session_id, идентификатор одноразового разрешения, TTL и отпечаток операции. Удаление `_approval_verified` из входных `arguments` защищает только от подделки **этого маркера**, но не от передачи `approved=True` вызывающим кодом.

В `src/leshy/action_approvals.py` `ApprovalBroker.consume(owner_id, approval_id)` проверяет owner и TTL, атомарно удаляет разрешение и возвращает сохранённый `BrowserAction`. Однако разрешение не привязано к session_id и каноническому отпечатку действия. Следовательно, наличие брокера само по себе не доказывает защищённость всех точек исполнения.

## Безопасный план интеграции

1. Инвентаризировать все вызовы `BrowserAgent.execute`, `approved=True`, `ApprovalBroker.consume`, прямые вызовы адаптеров и маршруты Web/Telegram/API. Отдельно проверить вызовы через LLM tools и автономные задачи.
2. Ввести серверный тип `VerifiedApprovalGrant` с неизменяемыми owner UUID, session_id, action digest, expiration и nonce; создавать его **только** внутри доверенного брокера после подтверждения пользователем. Не принимать этот тип или его поля непосредственно из HTTP, Telegram или LLM.
3. Для рискованных действий проверять grant непосредственно перед вызовом адаптера, сверяя owner/session/action digest; расходовать разрешение атомарно ровно один раз. Не считать `approved=True` доказательством разрешения. Сохранить совместимость READ-действий.
4. До интеграции всех входов оставить рискованные пути fail-closed. Миграции данных и объединение профилей не требуются; непривязанные Telegram user_id остаются изолированными.
5. После изменений повторно прочитать все изменённые файлы из `main` и подтвердить, что **каждый** runtime-вход проходит через проверку. Только затем считать реализацию завершённой.

## Обязательные регрессии (пока НЕ запущены)

| Сценарий | Ожидаемое поведение |
|---|---|
| Прямой `execute(..., approved=True)` без grant | Запрет MUTATE/COMMIT/FINANCIAL |
| Поддельный `_approval_verified` в arguments | Запрет |
| Чужой owner UUID / другая session_id | Запрет без расходования чужого grant |
| Изменённые URL, сумма, получатель или параметры | Запрет, новый запрос подтверждения |

| Недоступность брокера или отсутствие identity | Fail-closed, без обхода |
| Web/Telegram/API и прямой tool-call | Единая серверная проверка |

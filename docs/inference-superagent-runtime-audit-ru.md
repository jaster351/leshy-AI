# Аудит фактического маршрута фонового SuperAgent (11.11.2026)

База анализа: `main` = `2133b41967571af4adf0c2a7ec2e411c1bd5ad9b`. Это **статический аудит**, а не подтверждение выполнения runtime.

## Подтверждённая цепочка

- `src/leshy/superagent_scheduler.py:12-39`: `install_superagent_background_scheduler()` подменяет `SuperAgentService._execute` обёрткой `scheduled_execute`. При вызове она запрашивает `get_inference_scheduler(self.app)`, затем `scheduler.slot(source="superagent:<ticket_id>", priority=PRIORITY_BACKGROUND, cancel_event=self._stop, timeout=None)` и только после выдачи слота вызывает исходный `_execute`.
- `src/leshy/inference_scheduler.py:117-149`: `slot()` освобождает слот в `finally`, включая исключения из исходного `_execute`. `cancel_event` проверяется во время **ожидания**, но сам по себе не прерывает уже выполняющуюся генерацию.
- `src/leshy/background_backend.py`: `BackgroundAdaptiveLLM` предпочитает NPU, затем CPU, затем GPU. `from_interactive()` разделяет объекты провайдеров с интерактивным роутером; независимый scheduler не гарантирует изоляцию вычислительных ресурсов.
- `src/leshy/web_server_impl.py:356-359`: Web-диагностика читает `app.inference_scheduler.status()`; это **путь отображения**, а не доказательство постановки Web-запросов в очередь.

## Неподтверждённые условия интеграции

1. Установщик `install_superagent_background_scheduler()` должен реально вызываться при старте до первого `SuperAgentService._execute`. Наличие функции не доказывает вызов.
2. Нужно проверить, обёрнуты ли все интерактивные пути Web/Telegram/API в **тот же экземпляр** scheduler. Иначе приоритеты не защищают чат.
3. `timeout=None` означает неограниченное ожидание фоновой задачи; это не ограничение времени удержания слота.
4. Вытеснение уже запущенного backend требует явного cancellation API конкретного провайдера; принудительное освобождение логического слота без остановки inference может запустить параллельную нагрузку и повредить стабильность.
5. Для NPU/CPU→GPU fallback требуется отдельный контроль доступности GPU при интерактивной активности, не только порядок выбора провайдеров.

## Регрессионные сценарии для следующего изменения

- SuperAgent ожидает, затем Web и Telegram запрашивают слот: интерактивные запросы должны обгонять **ожидающий** фон.
- SuperAgent уже выполняется, Web поступает позже: документировать максимальную задержку и проверить кооперативную отмену, не симулировать вытеснение только `release()`.
- Отмена `self._stop` во время ожидания удаляет waiter, но не освобождает слот другого владельца.
- Исключение в `_ORIGINAL_EXECUTE` освобождает слот ровно один раз.
- При NPU HTTP 503 и CPU fallback маршрутизация не должна многократно ждать долгих timeout; переход на GPU не должен блокировать интерактивную сессию.
- Проверить Web/Telegram/API end-to-end и одинаковый экземпляр scheduler, включая запуск после перезагрузки.

Локальные сборки и тесты не запускались по ограничению владельца. Этот документ не означает, что отмена или изоляция GPU реализована.

## Диагностика инверсии приоритета (11.11.2026)

При поступлении более приоритетного запроса во время активной низкоприоритетной генерации планировщик однократно пишет `inference_priority_inversion` с `waiting_source`, `waiting_priority`, `active_source`, `active_priority`, `active_held_ms`. Это диагностический сигнал для оценки задержек Web/Telegram; он **не** останавливает и не вытесняет backend. Событие не должно содержать текст запросов или owner-секреты. Регрессия проверяет событие, сохранение активного фонового слота и отмену ожидающего Web-запроса. Локальные тесты и сборки не запускались. Для устранения задержек необходима проверенная end-to-end отмена на уровне backend.

## Дополнительные негативные сценарии очереди (11.11.2026)

`tests/test_inference_timeout_recovery.py` фиксирует два контракта: (1) Web-waiter, превысивший timeout во время активного фонового слота, удаляется из очереди и не препятствует последующему Telegram-запросу; (2) повторный `release()` старого waiter не может снять чужой активный слот. Эти проверки относятся только к диспетчеру и не доказывают отмену уже выполняющегося backend. Файл опубликован и повторно прочитан из ветки PR; тесты не запускались.

# Навык Лешего: отслеживание посылок через веб-сайты

## Цель

Пользователь должен иметь возможность отправить Лешему обычный трек-номер и попросить следить за посылкой. Леший должен научиться работать с сайтом отслеживания через браузер так же, как человек: открыть сайт, найти поле трек-номера, ввести значение, запустить поиск, дождаться результата, прочитать статус и затем периодически повторять проверку.

Первый целевой пример — сайт `https://gdeposylka.ru/`.

Этот навык не зависит от наличия API. Основной сценарий — browser/computer use.

## Команды пользователя

Леший должен понимать естественные формулировки:

- `Отследи посылку AB123456789CD`;
- `Следи за этим треком AB123456789CD`;
- `Добавь посылку AB123456789CD и сообщай, если статус изменится`;
- `Где сейчас моя посылка AB123456789CD?`;
- `Перестань следить за AB123456789CD`;
- `Покажи все мои посылки`;
- `Какие посылки уже доставлены?`.

Если в сообщении найден вероятный трек-номер, Леший не должен автоматически создавать вечную подписку без контекста. Разовая формулировка `где посылка` означает одну проверку; `следи / сообщай об изменениях` означает постоянное отслеживание.

## Распознавание трек-номера

Трек-номер рассматривается как пользовательское значение, а не как пароль или секрет.

Нельзя полагаться только на один жёсткий regex, потому что форматы перевозчиков различаются. Детектор должен сочетать:

- длину;
- буквы/цифры;
- известные международные форматы;
- контекст сообщения (`трек`, `посылка`, `отследи`, `доставка`);
- при необходимости проверку через сайт.

Если найдено несколько возможных треков, Леший должен обработать каждый отдельно либо уточнить, какой именно использовать, если контекст неоднозначен.

## Канонический сценарий через «ГдеПосылка»

### Шаг 1. Открыть сайт

Открыть `https://gdeposylka.ru/` в отдельной вкладке/контексте браузера.

После открытия:

- дождаться стабилизации страницы;
- определить, нет ли cookie/consent/информационного popup;
- прочитать интерфейс;
- найти форму отслеживания по смыслу.

Селекторы не должны быть захардкожены как единственный способ поиска. Интерфейс может измениться.

### Шаг 2. Найти поле трек-номера

Приоритет поиска:

1. DOM/accessibility role + label/placeholder;
2. текст рядом с полем;
3. OCR;
4. visual understanding;
5. координаты только после повторной проверки текущей геометрии.

Кандидат должен соответствовать назначению `поле для трек-номера` с достаточным confidence.

### Шаг 3. Ввести трек

Перед вводом Леший проверяет, что фокус находится в нужном поле.

После ввода он снова читает поле и подтверждает, что значение совпадает с исходным трек-номером.

### Шаг 4. Запустить отслеживание

Найти кнопку/действие со смыслом `отследить / найти / проверить` и активировать его.

После действия не считать запрос успешным до появления одного из подтверждённых состояний:

- найден результат;
- трек не найден;
- ошибка/недоступность;
- требуется действие пользователя;
- загрузка ещё продолжается.

### Шаг 5. Дождаться результата

Леший должен отличать:

- spinner/loading;
- пустую страницу;
- сетевую ошибку;
- сообщение `не найдено`;
- настоящую карточку/ленту отслеживания.

При медленной загрузке следует ждать по условиям состояния страницы, а не фиксированное число секунд.

### Шаг 6. Извлечь данные

Минимальная нормализованная структура результата:

```json
{
  "tracking_number": "...",
  "carrier": "...",
  "status": "...",
  "status_category": "in_transit|out_for_delivery|delivered|exception|unknown",
  "last_event_time": "...",
  "last_event_location": "...",
  "last_event_text": "...",
  "estimated_delivery": "...",
  "source": "https://gdeposylka.ru/...",
  "checked_at": "..."
}
```

Поля, которых сайт не показывает, остаются `null`/пустыми. Леший не должен додумывать перевозчика, дату или местоположение.

### Шаг 7. Визуально подтвердить извлечение

Леший обязан сверить нормализованный результат с реально видимым текстом страницы.

Если DOM и визуальный текст противоречат друг другу, результат отмечается `uncertain` и не должен молча сохраняться как достоверный.

## Постоянное отслеживание

Если пользователь сказал `следи`, создаётся постоянная запись.

Минимальные поля:

- `owner_id`;
- `tracking_number`;
- пользовательское имя посылки (опционально);
- `preferred_skill_id`;
- `preferred_site`;
- `carrier` (если определён);
- `last_status`;
- `last_status_category`;
- `last_event_time`;
- `last_event_location`;
- `last_event_text`;
- `last_checked_at`;
- `next_check_at`;
- `last_change_at`;
- `consecutive_failures`;
- `state`;
- `notify_channel`;
- `created_at`;
- `updated_at`.

## Период проверки

Леший не должен бессмысленно обновлять страницу каждую минуту.

Рекомендуемая адаптивная политика:

- новое отправление/в пути: примерно раз в 1–3 часа;
- `out_for_delivery`: чаще, например раз в 30–60 минут;
- отсутствие изменений долгое время: увеличивать интервал;
- сайт явно показывает собственный cooldown: уважать его;
- `delivered`: прекращать регулярные проверки;
- временная ошибка сайта: exponential backoff;
- `needs_user_action`: приостановить до участия пользователя.

Конкретные значения должны быть конфигурируемыми.

## Уведомления

Пользователь получает уведомление только при значимом изменении, если не попросил иначе.

Изменением считается:

- новый статус;
- новое событие;
- изменение местоположения;
- назначение доставки курьером;
- проблема/исключение;
- доставка завершена;
- появился новый трек, связанный со старым, если это подтверждено страницей.

Пример уведомления:

`Посылка AB123456789CD обновилась: прибыла в сортировочный центр, Челябинск. Последнее событие: 2 ноября 2026, 13:40. Проверено через ГдеПосылка.`

Не надо присылать сообщение `статус не изменился` после каждой фоновой проверки.

## Память

Леший должен запоминать:

- что пользователь отслеживает этот трек;
- как пользователь назвал посылку;
- последний подтверждённый статус;
- выбранный рабочий browser-skill;
- последнее время проверки;
- историю значимых изменений.

Не надо сохранять в долговременную память весь HTML страницы или каждое промежуточное визуальное состояние.

История статусов должна храниться структурированно и быть доступна для вопросов:

- `когда она приехала в Россию?`;
- `сколько дней без движения?`;
- `какой был предыдущий статус?`.

## Если «ГдеПосылка» не работает

Проблема одного сайта не должна ломать функцию отслеживания в целом.

Fallback-порядок:

1. повторить безопасную проверку после backoff;
2. проверить, не изменился ли интерфейс;
3. если browser-skill устарел — запустить repair/relearn;
4. определить перевозчика по данным уже полученной страницы или треку;
5. использовать другой разрешённый пользовательский веб-интерфейс перевозчика;
6. сообщить пользователю, какой источник фактически использован.

Леший не должен выдавать старый статус за свежий. Если свежая проверка не удалась, он сообщает дату последней успешной проверки.

## CAPTCHA, challenge и авторизация

Если сайт показывает CAPTCHA или challenge, который требует человека:

- не обходить его программно;
- остановить автоматические действия;
- сообщить `Нужно Ваше действие в браузере`;
- после прохождения пользователем продолжить с текущей страницы;
- не записывать ответ CAPTCHA как часть навыка.

Если сайт требует логин:

- использовать обычную пользовательскую сессию браузера после разрешения;
- пароль/OTP не сохранять в обычной памяти;
- после успешной авторизации навык может использовать существующую сессию, пока она действительна.

## Самообучение именно этого навыка

Пользовательская команда:

> Научись работать с ГдеПосылка как человек. Я буду присылать трек-номер. Ты должен открыть сайт, проверить посылку, запомнить статус и, если я сказал следить, самостоятельно сообщать об изменениях.

Должна запускать `Browser Skill Builder`:

1. `observe` — открыть сайт и изучить интерфейс;
2. `map` — найти форму и состояния результата;
3. `draft` — создать candidate-навык;
4. `dry-run` — прогнать безопасный сценарий;
5. `verify` — визуально подтвердить результат;
6. `persist` — сохранить навык;
7. `subscribe` — при необходимости создать постоянную задачу;
8. `monitor` — выполнять проверки;
9. `repair` — переобучить изменившийся интерфейс;
10. `rollback` — вернуть предыдущую рабочую версию при неудачном repair.

## Тестовые сценарии

Обязательные автоматические/интеграционные тесты:

1. валидный трек и успешный результат;
2. неизвестный трек;
3. медленный ответ сайта;
4. временная HTTP/сетевая ошибка;
5. изменение DOM при сохранённом визуальном смысле;
6. popup поверх формы;
7. изменение размера браузера;
8. CAPTCHA -> `needs_user_action` без попытки обхода;
9. повторная проверка без изменения -> нет уведомления;
10. смена статуса -> ровно одно уведомление;
11. `delivered` -> прекращение регулярного polling;
12. перезапуск Лешего -> подписка и последнее состояние восстановлены;
13. два разных трека -> независимые состояния;
14. один и тот же трек добавлен повторно -> отсутствие дублирующей подписки;
15. устаревший skill -> repair, а не слепые клики.

## Критерий готовности

Пользователь должен иметь возможность один раз научить Лешего работе с сайтом, после чего сценарий выглядит так:

1. пользователь пишет трек-номер;
2. Леший распознаёт намерение;
3. открывает сайт;
4. выполняет браузерный навык;
5. возвращает подтверждённый статус;
6. по команде `следи` сохраняет подписку;
7. самостоятельно проверяет позже;
8. сообщает только об изменениях;
9. после перезапуска продолжает работу;
10. при изменении интерфейса сайта пытается переобучить навык, а не ломает всю функцию.

Это является первым эталонным примером общего механизма `Browser Skill Learning`, а не специальным хардкодом только для одного сайта.

# Обучение Лешего работе с веб-сайтами как человека

## Назначение

Леший должен уметь осваивать новый веб-сайт не только через API и не только как источник текста. Целевой режим — работа через обычный пользовательский интерфейс браузера так, как это делает человек: открыть страницу, увидеть элементы, понять назначение формы, ввести данные, нажать нужную кнопку, дождаться результата, прочитать его и проверить, что действие действительно выполнено.

Это отдельный класс обучения: **обучение навыку взаимодействия с интерфейсом**.

Базовый цикл:

`задача пользователя -> исследование сайта -> наблюдение интерфейса -> построение карты действий -> пробный прогон -> проверка результата -> сохранение навыка -> повторное использование`

Навык не должен сводиться к набору координат мыши. Сайт может изменить масштаб, положение элемента, тему, текст кнопки или верстку. Поэтому Леший должен хранить смысловые признаки элементов и уметь повторно находить их.

## Принцип «как человек»

При работе с сайтом Леший должен:

1. открыть сайт в реальном браузере;
2. дождаться загрузки страницы;
3. прочитать видимый интерфейс;
4. при возможности использовать DOM/accessibility tree;
5. при недостаточности DOM использовать OCR и локальное visual understanding;
6. определить поле, кнопку или другой элемент по смыслу;
7. выполнить одно действие;
8. снова увидеть страницу;
9. подтвердить ожидаемое изменение;
10. только после проверки переходить к следующему действию.

Канонический цикл Computer Use остаётся обязательным:

`увидел -> понял -> сделал -> снова увидел -> подтвердил`

Запрещено считать действие успешным только потому, что был отправлен click/input event.

## Чем этот режим отличается от API

API — только один из возможных способов интеграции. Если пользователь просит научиться работать с обычным сайтом через браузер, наличие или отсутствие API не определяет возможность обучения интерфейсу.

Для browser-skill Леший действует на уровне пользовательского интерфейса и не должен автоматически подменять этот сценарий API-интеграцией.

При этом Леший может знать о существовании API и использовать это знание для понимания предметной области, но конкретный сохранённый навык `browser` должен воспроизводить пользовательский путь через сайт.

## Границы

Леший не должен:

- обходить CAPTCHA или anti-bot challenge;
- обходить авторизацию, MFA или ограничения доступа;
- скрытно эмулировать пользователя для обхода технических блокировок;
- использовать украденные cookie/session/token;
- продолжать рискованное действие, если сайт явно требует подтверждения пользователя;
- сохранять пароль, OTP, банковские реквизиты или другие секреты в обычной долговременной памяти;
- выполнять платёж, покупку, удаление данных, изменение безопасности или юридически значимое действие без применимого Human Approval Gate.

Если сайт показывает CAPTCHA, challenge, MFA или иной шаг, который должен выполнить пользователь, навык переходит в состояние `needs_user_action`, показывает причину и продолжает после завершения этого шага пользователем.

## Модель browser-skill

Сохранённый навык должен быть декларативным и версионируемым. Минимальная структура:

- `skill_id` — стабильный идентификатор;
- `name` — человекочитаемое русское имя;
- `site_hosts` — разрешённые домены;
- `purpose` — назначение;
- `input_schema` — входные данные;
- `steps` — смысловая последовательность действий;
- `element_hints` — признаки целевых элементов;
- `success_conditions` — как подтвердить результат;
- `failure_signatures` — известные ошибки/изменения интерфейса;
- `data_extractors` — какие данные извлекать со страницы;
- `refresh_policy` — когда навык требуется перепроверить;
- `risk_level` — уровень риска;
- `approval_policy` — действия, требующие подтверждения;
- `created_from` — происхождение навыка;
- `learned_at` / `last_verified_at`;
- `version`;
- `status` — `candidate`, `verified`, `stale`, `disabled`;
- `test_cases` — проверочные сценарии;
- `rollback_to` — предыдущая рабочая версия.

## Смысловой поиск элементов

Для каждого элемента нельзя сохранять только `x/y`.

Леший должен хранить несколько независимых признаков:

- role: `textbox`, `button`, `link`, `list`, `status`;
- видимый текст;
- placeholder;
- accessible name/label;
- CSS/DOM признаки как дополнительный, но не единственный сигнал;
- ближайший заголовок/подпись;
- относительное положение;
- визуальный шаблон, если DOM недоступен.

Выбор элемента должен оцениваться по confidence. Если найдено несколько равноценных элементов или confidence слишком низкий, действие не выполняется вслепую.

## Самообучение новому сайту

Команда пользователя может звучать естественно:

> Научись работать с этим сайтом и отслеживать там мои посылки.

Леший должен выполнить следующий учебный сценарий.

### 1. Определить цель

Не просто «изучить сайт», а выделить конкретный навык, например:

- найти форму отслеживания;
- ввести трек-номер;
- запустить проверку;
- дождаться результата;
- извлечь текущий статус;
- извлечь время/место последнего события;
- сохранить последнее наблюдаемое состояние;
- повторно проверить позже.

### 2. Провести исследовательский проход

В безопасном режиме без необратимых действий:

- открыть главную страницу;
- определить навигацию;
- найти целевую форму;
- построить карту элементов;
- зафиксировать варианты текстов и состояний;
- обнаружить ошибки валидации;
- определить признаки успешного результата;
- определить признаки отсутствия данных;
- определить состояния загрузки/таймаута;
- определить необходимость cookie/consent/авторизации.

### 3. Создать candidate-навык

Первый результат всегда имеет статус `candidate`. Он не считается надёжным только потому, что однажды сработал.

### 4. Проверить навык

Минимальный Quality Gate:

- повторный запуск в новой вкладке;
- запуск после reload;
- изменение размера окна;
- проверка при медленной загрузке;
- корректная обработка неизвестного/ошибочного входа;
- проверка, что извлечённые данные действительно видны на странице;
- отсутствие действий по старым координатам после изменения интерфейса.

После успешных тестов навык становится `verified`.

### 5. Использовать повторно

При следующей команде Леший сначала пробует `verified`-навык. Если интерфейс изменился и success condition не подтверждён, он не угадывает дальнейшие клики, а запускает адаптацию.

## Автоматическая адаптация навыка

Если сайт изменился:

1. старая версия отмечается `suspect`/`stale`;
2. выполняется повторное наблюдение;
3. Леший пытается сопоставить старые смысловые элементы с новыми;
4. создаётся новая candidate-версия навыка;
5. выполняются regression-тесты;
6. новая версия становится рабочей только после подтверждённого результата;
7. сохраняется возможность rollback.

## Периодические задачи

Browser-skill может использоваться в фоновых задачах, если пользователь явно создал постоянную задачу, например отслеживание отправления.

Для фоновой проверки обязательно хранить:

- владелец;
- skill_id + version;
- входные данные задачи;
- последний подтверждённый результат;
- время последней успешной проверки;
- время следующей проверки;
- число последовательных ошибок;
- состояние `active / delivered / paused / needs_user_action / failed`;
- канал уведомления.

Уведомление отправляется только при значимом изменении, если пользователь не указал иное.

## Не путать знания и навыки

В базе знаний Леший может хранить факт: «на странице есть форма отслеживания». Это не означает, что он умеет надёжно пользоваться формой.

Навык считается освоенным только при наличии:

- последовательности действий;
- проверок состояния;
- success condition;
- тестов;
- сохранённой версии;
- результата повторного прогона.

Поэтому архитектурно нужны два контура:

`Research/Learning -> знания`

и

`Browser Skill Learning -> исполнимый проверяемый навык`.

## Связь с существующей архитектурой Лешего

Эта документация развивает уже зафиксированные принципы:

- `docs/HUMAN_LEARNING.md` — обучение из человеческих источников;
- `docs/COMPUTER_USE_1.10.3.md` — работа с интерфейсом по циклу наблюдение → действие → повторное наблюдение;
- Human Approval Gate — подтверждение рискованных действий;
- долговременная память — хранение пользовательской задачи, но не секретов;
- provenance/audit — журнал фактически выполненных действий;
- self-learning — исследование нового сайта и создание candidate-навыка.

## Обязательный Skill Builder

Для полной автономности Лешему нужен `Browser Skill Builder` со стадиями:

`observe -> map -> draft -> dry-run -> verify -> persist -> monitor -> repair/rollback`

Skill Builder должен уметь:

- получать цель на естественном языке;
- исследовать сайт в sandbox browser context;
- создавать декларативное описание навыка;
- генерировать проверочные сценарии;
- выполнять безопасные прогоны;
- сравнивать ожидаемый и фактический UI;
- версионировать навык;
- выдавать понятный пользователю отчёт;
- автоматически перепроверять навык после изменения сайта;
- не изменять основную модель ради одного сайта.

## Критерий готовности

Функция считается реализованной, когда пользователь может написать:

> Научись на сайте X делать Y.

и Леший без ручного программирования конкретного сайта способен:

1. открыть сайт;
2. освоить безопасный пользовательский путь;
3. сохранить проверяемый навык;
4. повторить его после перезапуска;
5. заметить изменение интерфейса;
6. адаптировать навык или запросить помощь;
7. журналировать действия;
8. не ломать уже проверенные навыки при обучении новому сайту.

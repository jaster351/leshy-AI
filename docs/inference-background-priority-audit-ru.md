# Приоритет фонового inference: границы и регрессии (Issue #100)

Основа аудита: `main` `2133b41967571af4adf0c2a7ec2e411c1bd5ad9b` (10.11.2026).

## Что подтверждено исходниками

`src/leshy/inference_scheduler.py` сериализует доступ к одному inference slot. Очередь сортируется по убыванию priority и FIFO при равном priority: Web=100, Telegram=70, background=10. Отмена и timeout удаляют ожидающую заявку. **Уже активный запрос не вытесняется**: приоритет не гарантирует интерактивную latency, если длительный auto-title успел захватить слот.

`src/leshy/background_backend.py` предпочитает NPU, CPU, GPU, но GPU остаётся допустимым fallback. Общие provider-объекты могут конкурировать с пользовательским чатом. Наличие класса маршрутизатора само по себе не доказывает, что все фоновые вызовы идут через него.

## Что добавлено

`tests/test_inference_scheduler_priority_regression.py` покрывает порядок при одновременном ожидании Web/background, отмену ожидающего background, timeout без утечки очереди и назначение приоритетов. Это **только контракт очереди**, а не подтверждение preemption или E2E auto-title. Тесты не запускались по требованию владельца.

## Что остаётся сделать до runtime-исправления

1. Найти фактический producer `leshy-session-auto-title` и проследить Web/Telegram -> постановка задачи -> provider -> scheduler. Поиск по индексированному GitHub code search результатов не дал; это не доказательство отсутствия кода.
2. Исключить массовую обработку старых сессий при старте; ограничить количество и длительность фоновых генераций, исключить повторное планирование при рестарте.
3. Перед началом background LLM проверять интерактивный спрос; обеспечить отмену/дедлайн для длительной генерации и безопасный отказ, не удаляя заголовки и историю.
4. Проверить fallback NPU -> CPU -> GPU при активном пользовательском GPU и health/circuit breaker для OpenVINO 503.
5. Добавить E2E regression на 83-секундный auto-title, рестарт с историей и одновременный пользовательский запрос; затем read-back всех runtime точек. Не заявлять об исправлении Issue #100 до проверки.

Документ фиксирует границы проверки, а не готовность runtime.

# Актуальность памяти и текущие источники GraphRAG

Issue #99, Codex, ветка `codex/99-memory-freshness-graph`, подготовка 1.10.198. Отдельный этап после #332: основа f5573060be7166095ff1ef67e8f35e6c2fa383b6, main b4bfd27faa3535ef9a77b6ffe5dc4e43e49f27b4. До интеграции #332 этот этап должен оставаться зависимым PR.

## Причина

Базовый `_memory_context` читал восемь записей без проверки срока; фильтр интеллектуальной памяти не защищал уже добавленный базовый блок. GraphRAG сохранял копии текстов и связи, а при поиске не сверял их с исходными memories/knowledge. Удалённая, истёкшая, изменённая или отозванная запись могла вернуться через кэш. Один интервал `_last_sync` на все профили также позволял активности одного владельца откладывать индексацию другого.

## Базовая память

Чистый `memory_is_fresh` используется без чтения хранилища: None/пустой срок — постоянный, валидный ISO строго позже текущего времени — действующий; неверный тип/формат и истечение отклоняются. Наивный ISO понимается как UTC, а не локальная зона Windows. Существующие данные не переписываются.

Базовый контекст последовательно читает пары ID/срока порциями до128 строк с прежними фильтрами owner и исключением dialogue_rule/owner_knowledge_document. Останавливается после восьми живых ID или конца курсора; общего лимита до проверки срока нет. Поэтому более1000 истёкших записей перед живой памятью не скрывают её навсегда. Затем отдельный ограниченный запрос читает только выбранные тексты, повторно проверяя owner/kind; срок проверяется снова перед добавлением в контекст. Постоянные правила загружаются прежним отдельным механизмом. Интеллектуальная память использует тот же TTL-предикат; owner при чтении и формировании fingerprint не обрезается до общего префикса.

## GraphRAG — область текущей реализации

Кэш и его payload не являются самостоятельным источником истины. Перед ответом требуется текущая исходная строка по строгому ID, точный owner, допустимый тип/статус/срок, актуальный текст и связь с концептом. Частная memory из shared-ветви не становится общей; Knowledge использует действующие проверки trusted, актуальности и целостности, а также ограничения полного запроса для CVE/GHSA и точных версий. Отсутствующая или изменённая строка не возвращается как прежнее утверждение даже внутри интервала синхронизации.

Изменения источников не удаляются и не мигрируют. Допускается перестроение только производных `mentions`-связей индексируемого факта. Интервалы синхронизации относятся к конкретному типу/владельцу и учитываются после успешного commit; ошибка не должна запрещать следующий повтор. Нельзя считать наличие кэшированного узла доказательством существования и актуальности исходника.

Синхронизация читает источники курсором порциями до128 строк. Для текущего типа/владельца сначала собирается ограниченный список пригодных полных строк: до1200 знаний или1000 воспоминаний. Бюджет применяется после проверок актуальности и пригодности, а не к истёкшему префиксу. Курсор источника закрывается в `finally`, в том числе при ранней остановке, и только затем `_link_fact` записывает подготовленные факты. Поэтому128 — размер читаемой порции, а не предел всех одновременно удерживаемых строк: подготовленный список достигает1200/1000. Это ограничение числа индексируемых живых фактов, а не обещание полноты всей базы: живые записи за этим бюджетом могут требовать отдельной стратегии индексации. При очень большом числе непригодных строк обход может прочитать весь соответствующий набор; общее время сканирования и сортировки SQLite не ограничено.

Закрытие читающего курсора до первой записи устраняет переход активного read snapshot к write после чужого commit в WAL. Сканирование до первой записи не резервирует writer через `BEGIN IMMEDIATE`; если предыдущий тип уже записан, следующий скан выполняется внутри той же незавершённой транзакции записи. Между подготовкой списка и его записью источник может измениться: актуальность, owner, доверие и соответствие текста повторно проверяются `search` по текущим исходным строкам перед выдачей ответа. Ошибка записи или commit откатывает весь sync; часы обновляются только после успешного commit. Подготовка списка не заменяет проверку реальной конкуренции нескольких соединений.

Приоритет и источник берутся из текущей исходной строки. Нулевой вес не заменяется высоким значением по умолчанию: сохраняется прежний нижний предел0,2. Перед фильтром KnowledgeBase добавлена проверка границ целого CVE/GHSA: CVE-2026-1000 не совпадает с CVE-2026-10000 или идентификатором с буквенным продолжением. Общий поиск слов KnowledgeBase сохраняет прежнюю подстрочную семантику; строгий поиск по всем токенам этим PR не реализован. Отдельные проверки полного owner относятся к Engine/Graph и их SQL, а не к общей смене identity-протокола: в других legacy-путях профиля/сессии остаётся собственная нормализация, в том числе ограничение длины. Эти границы требуют отдельной задачи; тесты длинных ID не доказывают универсальную изоляцию всего Web/Telegram runtime.

## Проверка и ограничения

Подготовлен `tests/test_memory_freshness_graph.py`, ровно девять test methods: UTC/границы/ошибочный срок и retrieve; базовый контекст с истёкшей первой восьмёркой и ограниченным чтением текстов; current-source проверка deleted/edited/expired памяти и текущего provenance/нулевого веса; trust/TTL/Unicode/CVE/версии знаний; независимость владельцев внутри cooldown; повтор после ошибки commit; private/shared/чужие target/ID/длинные owner; перестроение только derived mentions; живой tail-ID и пределы соседей/параметров. Выбранные реальные определения извлекаются из AST, SQLite создаётся только при запуске теста как `:memory:`, часы и диагностика подменены. Это не пользовательская база.

20.11.2026 после отдельного явного разрешения владельца выполнен только этот файл: `python tests/test_memory_freshness_graph.py`, девять проверок пройдены за 0,270 с на исходном SHA `29142dd2c4e40399cd913a3df8c6af8d4166dbdf`. После замечаний независимого review5985335453 те же девять методов дополнены случаями >1000 истёкших записей перед живой базовой памятью, >1200/1000 непригодных источников перед живыми Graph-фактами и CVE/GHSA с общим префиксом. Исправление прошло повторно:9/9, 0,261 с. Также выполнены AST, чтение изменённых блоков и diff/check. Приложение, модели, реальная сеть, фоновые потоки и пользовательский LeshyBrain не запускались; другие тесты, сборки и Actions этим разрешением не охватываются. Эти изолированные проверки не заменяют независимое Review-by-ChatGPT нового SHA и приёмку реального приложения.

В существующий сценарий ошибки commit добавлена проверка порядка: перед каждым вызовом `_link_fact` все открывавшиеся курсоры сканирования источников должны иметь отметку закрытия. Она выполняется на том же единственном синтетическом SQLite-соединении, без нового test method; это не двухсоединительная проверка WAL. После дополнения те же девять разрешённых методов пройдены:9/9 за 0,524 с. Риск повышения активного read snapshot к write описан в [документации SQLite](https://www.sqlite.org/rescode.html#busy_snapshot); проверка двух реальных файловых соединений здесь не выполнялась.

Реальный Web/Telegram/LLM сценарий, обновление установки и полнота качества RAG ещё не проверены. Это фильтрация ответов по текущему источнику, а не физическое стирание всех старых копий из SQLite: политика полного удаления/резервных копий требует отдельной задачи. Пределы выборки могут ограничивать полноту; нельзя объявлять отсутствие записи в ограниченном окне доказательством отсутствия знания вообще.

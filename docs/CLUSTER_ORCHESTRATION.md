# Кластерный оркестратор Лешего

## Назначение

Леший должен уметь использовать один или несколько компьютеров как общий пул ресурсов, не теряя контекст, текст ответа и связь с исходным пользовательским каналом.

Канал пользователя всегда принадлежит исходному узлу (`origin_node_id`). Если вопрос пришёл из Web, итоговый поток возвращается в тот же Web-сеанс. Если вопрос пришёл из Telegram, результат возвращается исходному Telegram-сеансу.

## Локальная очередь

Все обращения к локальной LLM проходят через `InferenceScheduler`.

Приоритеты:

1. Web и голосовой Web — 100.
2. Telegram — 70.
3. Интерактивные системные действия — 60.
4. Startup recovery — 30.
5. Фоновые задачи и самообучение — 10.

При одинаковом приоритете действует FIFO. Уже начатый пользовательский ответ не обрывается. Следующий свободный inference-slot получает самая приоритетная ожидающая задача.

## Обнаружение узлов

Discovery отделён от транспорта задач. Узел публикует:

- постоянный `node_id`;
- сетевой endpoint;
- CPU threads;
- GPU/NPU;
- доступные модели;
- текущую загрузку;
- глубину очереди;
- готовность принимать задания;
- heartbeat/`last_seen`.

Tracker, DHT, mDNS или другой механизм могут реализовать один контракт `PeerDiscovery`. Это позволяет начать с tracker-подобного реестра и позднее добавить децентрализованный discovery без переделки Web, Telegram и LLM-кода.

## Распределение работы между компьютерами

Основной режим — `cooperative`.

Исходный компьютер является ведущим. Он создаёт `ClusterTask`, сохраняющий:

- `task_id`;
- `origin_node_id`;
- `reply_to`;
- `owner_id`;
- `session_id`;
- `request_id`;
- приоритет;
- требования к CPU/GPU/NPU;
- модель;
- TTL.

Оркестратор выбирает подходящий узел с учётом его ресурсов, очереди и нагрузки. Второй компьютер может параллельно выполнять поиск, RAG, анализ документов, инструменты, проверку фактов, ASR/TTS и другие независимые части работы. Результаты возвращаются ведущему по `task_id`, после чего ведущий формирует единый итоговый ответ.

Нельзя просто попросить две независимые LLM сгенерировать по половине одного ответа и склеить токены. Это может дать повторы, пропуски и логические разрывы. Поэтому итоговый пользовательский поток принадлежит одному ведущему узлу.

## Настоящий distributed inference

Режим `model_parallel` зарезервирован для будущего распределения одной совместимой модели между несколькими узлами через tensor/pipeline parallelism. Он разрешается только при совместимых модели, runtime и протоколе распределённого inference.

## RabbitMQ

RabbitMQ планируется как один из транспортов задач и результатов, но не как механизм discovery.

Заранее закреплены логические exchange:

- `leshy.cluster.tasks` — задания;
- `leshy.cluster.results` — результаты;
- `leshy.cluster.nodes` — события узлов;
- `leshy.cluster.dead` — dead-letter.

Результат маршрутизируется обратно на `origin_node_id`. Благодаря этому вычисление может выполняться на другом компьютере, а пользователь получает ответ в том интерфейсе, где задал вопрос.

## Отказоустойчивость

Задача имеет `task_id`, `origin_node_id`, TTL и проверку соответствия результата исходному заданию. В будущем транспорт должен поддерживать подтверждения, повторную доставку, идемпотентность, heartbeat узлов и requeue задачи при исчезновении исполнителя.

## Главное правило производительности

Распределённые и фоновые задачи не должны ухудшать скорость интерактивного Web-чата. Эталонная отзывчивость текущего быстрого Web-stream сохраняется как приоритет архитектуры.

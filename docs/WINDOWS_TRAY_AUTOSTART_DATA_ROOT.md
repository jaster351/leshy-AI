# Windows: System Tray, автозапуск и настраиваемое хранилище данных

Статус: обязательное требование для будущих Windows-сборок Leshy AI. Текущую приоритетную сборку «чат + Telegram + Web UI + память + интернет-поиск + управляемое самообучение» это требование не должно задерживать, если реализация ещё не готова.

## 1. System Tray

Windows-версия Лешего должна уметь работать через системный трей.

Обязательное поведение:
- после запуска может работать в фоне с иконкой в System Tray;
- клик по иконке открывает основной интерфейс;
- контекстное меню содержит как минимум: «Открыть Лешего», «Открыть Web UI», «Состояние», «Настройки», «Перезапустить», «Выйти»;
- закрытие главного окна не обязано завершать Лешего: пользователь может выбрать поведение «Свернуть в трей» или «Завершить»;
- команда «Выйти» в трее действительно останавливает локальный runtime и фоновые задачи;
- ошибки запуска/модели/Telegram/самообучения отображаются понятным статусом, а не молчаливым падением процесса.

## 2. Автозапуск

В настройках Windows-клиента должен быть явный переключатель:

**Запускать Лешего вместе с Windows: ВКЛ / ВЫКЛ**

Требования:
- пользователь может включить и выключить автозапуск без ручного редактирования реестра, Task Scheduler или папки Startup;
- выбранное состояние сохраняется после перезапуска и обновления;
- автозапуск по умолчанию не должен включаться скрытно без согласия пользователя;
- отдельная настройка определяет, показывать окно после автозапуска или запускать Лешего свёрнутым в System Tray;
- обновление приложения не должно самопроизвольно менять настройку автозапуска.

## 3. Корень пользовательских данных

`AppData` не является жёстко заданным местом хранения данных Лешего.

Правило:
- `AppData` может использоваться только как безопасный путь по умолчанию на чистой установке;
- пользователь должен иметь возможность выбрать собственный каталог данных при первой настройке и позже изменить его в настройках;
- фактический корень `LeshyBrain` должен определяться через единый Data Root Resolver, а не через разбросанные по коду абсолютные пути;
- все компоненты должны получать путь к данным через этот единый слой.

Под пользовательским корнем данных понимаются как минимум:
- `leshy.db`;
- `models/`;
- `shared-knowledge/`;
- `logs/`;
- пользовательские настройки;
- состояния памяти и сессий;
- локальные кэши, которые относятся к пользователю;
- Telegram-конфигурация и другие локальные данные, если их политика безопасности не требует отдельного защищённого системного хранилища.

## 4. Где хранить указатель на выбранный путь

Чтобы приложение после перезапуска могло найти пользовательский каталог, допускается хранить в стандартном профиле Windows только небольшой bootstrap/locator — например, один конфигурационный файл или эквивалентную запись Windows.

В этом bootstrap хранится только ссылка на фактический Data Root и минимальные метаданные. Основной `LeshyBrain` там хранить необязательно.

## 5. Изменение пути существующей установки

Кнопка «Изменить расположение данных» должна выполнять безопасную миграцию, а не просто менять строку пути.

Последовательность:
1. остановить запись в БД и фоновые задачи;
2. проверить доступность и свободное место назначения;
3. скопировать данные во временный каталог назначения;
4. проверить целостность основных файлов/БД;
5. атомарно переключить Data Root;
6. запустить Лешего из нового расположения и выполнить smoke-check;
7. старые данные удалять только после явного подтверждения пользователя или оставлять как резервную копию по выбранной политике;
8. при ошибке выполнить rollback на старый путь.

Нельзя допускать одновременную работу с двумя независимыми копиями `LeshyBrain` как будто это одна база.

## 6. Недоступный пользовательский путь

Если выбранный диск, NAS, сетевой путь или внешний накопитель временно недоступен:
- Леший должен показать понятную ошибку и предложить повторить подключение/выбрать другой путь;
- нельзя молча создавать новый пустой `LeshyBrain` в `AppData`;
- нельзя переключаться на другой каталог без явного решения пользователя;
- режим только для чтения допустим только если он технически безопасен и явно отображается пользователю.

## 7. Поддерживаемые варианты хранения

Архитектура должна позволять использовать:
- локальный SSD/HDD;
- другой внутренний диск;
- внешний диск;
- пользовательский каталог вне `AppData`;
- UNC/сетевой путь, если он доступен и удовлетворяет требованиям к блокировкам/целостности;
- NAS как пользовательское хранилище там, где это безопасно для используемой БД и файловой модели.

При выборе сетевого пути UI должен предупреждать о возможной потере производительности и недоступности сети. Для SQLite/других компонентов, чувствительных к сетевой файловой системе, должна быть отдельная проверка совместимости, а не безусловное разрешение.

## 8. Разделение программы и данных

Бинарники/установочные файлы Лешего и пользовательские данные должны рассматриваться как разные сущности.

Обновление приложения:
- не меняет пользовательский Data Root;
- не переносит данные обратно в `AppData`;
- не удаляет пользовательские модели, знания, память и настройки;
- использует миграции формата данных с резервной копией и возможностью отката.

## 9. Quality Gate для Windows

Перед тем как считать эти функции готовыми, нужны regression/smoke-тесты:
- запуск с Data Root по умолчанию;
- запуск с пользовательским Data Root на другом диске;
- сохранение выбранного пути после перезапуска;
- сохранение выбранного пути после обновления;
- безопасная миграция данных между дисками;
- rollback при неудачной миграции;
- отсутствие скрытого fallback в `AppData` при недоступном пользовательском пути;
- включение/выключение автозапуска;
- запуск в трей без открытия главного окна;
- открытие интерфейса из трея;
- корректное завершение через «Выйти»;
- отсутствие потери данных при закрытии окна и работе через трей.

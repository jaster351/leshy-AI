# Идемпотентность пользовательских запросов

## Цель

Один пользовательский запрос должен приводить максимум к одной генерации и одному логическому ответу независимо от интерфейса: Web, Windows/WebView, Telegram или прямого Runtime/API.

## Request ID

Каждый запрос получает `request_id`. Повторная доставка того же запроса обязана использовать тот же ID.

- Web streaming создаёт UUID на стороне клиента и передаёт его в `/v1/chat/stream`.
- Обычный `/v1/chat` также получает `request_id`; последний Web-слой добавляет его автоматически, если вызывающая сторона не передала ID.
- Telegram использует детерминированный ID `telegram:<chat_id>:<message_id>`. Повтор одного Telegram Update поэтому не запускает вторую генерацию.

## Устойчивый ledger

Состояние запросов хранится в основной SQLite-базе LeshyBrain в таблице `chat_request_ledger`.

Статусы:

- `in_progress` — запрос принят и выполняется;
- `done` — готовый результат сохранён, повтор не генерируется заново;
- `failed` — предыдущая попытка завершилась ошибкой и может быть безопасно повторена с тем же ID.

Ledger переживает перезапуск приложения. Устаревшая запись `in_progress`, оставшаяся после аварийного завершения процесса, может быть повторно захвачена после lease-периода. Один `request_id` нельзя использовать от имени другого владельца.

## Web-защита

Последний загружаемый `chat-idempotency.js` защищает от повторного вызова отправки одним кликом или одним нажатием Enter, даже если legacy/recovery/UI-слои одновременно подписаны на событие. Серверная защита остаётся обязательной: клиентская блокировка сама по себе не считается достаточной.

## Telegram

Telegram-защита выполняется до запуска LLM. Если один и тот же `message_id` получен повторно из polling/recovery, второй обработчик получает уже существующий ledger-entry и не отправляет второй ответ.

## Диагностика

Для расследования дублей журналируются события:

- `chat_request_claimed`;
- `chat_request_completed`;
- `chat_request_reclaimed`;
- `chat_duplicate_suppressed`;
- `telegram_duplicate_message_suppressed`;
- `chat_request_owner_collision`.

Секреты и полный текст пользовательского запроса в этих событиях не логируются.

## Regression Gate

Обязательно проверяются сценарии:

1. два независимых обработчика одновременно пытаются захватить один `request_id` — выигрывает только один;
2. повтор после готового ответа получает сохранённый результат без второй генерации;
3. ledger работает после повторного открытия базы/перезапуска;
4. один request ID от другого владельца отклоняется;
5. failed-запрос можно повторить;
6. Telegram `chat_id + message_id` даёт стабильный ID и различает разные сообщения.

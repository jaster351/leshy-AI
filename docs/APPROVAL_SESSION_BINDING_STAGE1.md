# Привязка Browser Approval к сессии — PR #69

Статус: **код этапа 2 в черновом PR; не объединён и не подтверждён E2E**.
Этап 1 добавил `session_id` в `PendingApproval` и методы `ApprovalBroker`.
Этап 2 связывает создание и использование браузерных подтверждений с серверной сессией.

## Что изменено в ветке

- `BrowserPlatform.request_external_action` и `resolve_approval` проверяют существование пары `sessions(id, owner_id)` и передают `session_id` в брокер; для опасных действий запрещён общий `web:local`.
- `ApprovalBroker` различает legacy-режим без сессии и новые сессионные разрешения. Вызов с `session_id` **не может** подтвердить старое разрешение без сессии; одноразовое извлечение выполняется под блокировкой.
- Web GET `/v1/browser/approvals?session_id=...` и POST `/v1/browser/approvals/resolve` требуют действительную серверную HttpOnly cookie профиля. Владелец берётся только из cookie, а не из query/JSON. Дополнительно проверяется, что диалог принадлежит этому владельцу. Один только API bearer token не даёт доступа к этим маршрутам.
- Панель Web показывает разрешения только текущего диалога (`leshy.session`), отправляет `session_id` и отклоняет попытку подтвердить карточку после переключения диалога. Частота фонового опроса снижена с 2,2 до 5 секунд; сохранён немедленный опрос при смене сессии.
- `web_server_impl11._body` не допускает подменённый `owner_id` при создании опасных Browser Approval из HTTP-чата без действующей cookie. Обычный неопасный чат сохраняет совместимость.
- Добавлены регрессии: чужой владелец, другая сессия того же владельца, удалённая сессия, одноразовость, legacy-разрешение, отсутствие/неверный идентификатор.

## Безопасное поведение при несовместимости

- **Web без действующей cookie** не может просмотреть или исполнить Browser Approval. Пользователь должен открыть Web-интерфейс, чтобы установить cookie; произвольный `owner_id` этого не заменяет.
- **Только bearer/API-клиент** не получает права подтверждать действие от имени произвольного пользователя. Отдельная аутентификация машинных клиентов и серверные токены полномочий потребуют самостоятельной реализации.
- **Telegram** может создать запрос с собственной проверенной сессией через обычный runtime, но канал подтверждения в Telegram отдельно ещё не реализован. Нельзя выдавать клиентский `approved=True` за подтверждение. Временно доступно безопасное отклонение неподдерживаемых маршрутов.
- Старый вызов `ApprovalBroker` без `session_id` сохраняет legacy-совместимость только внутри старого API брокера; Web-маршрут не исполняет такие разрешения. Окончательное удаление legacy требует инвентаризации всех внутренних вызовов.

## Что ещё блокирует статус «готово»

1. Дождаться успешного CI на **последнем** SHA PR и провести E2E-проверки Web с настоящей cookie, переключением диалогов и сценарием повторного POST. Локальные сборки/тесты без разрешения не запускались.
2. Подключить безопасный сценарий подтверждений через Telegram и API с независимой серверной проверкой источника и принадлежности сессии. Не использовать голый `owner_id` как доказательство аутентификации.
3. Устранить оставшиеся обходы через `approved=True` в других действиях/инструментах, где не используется `ApprovalBroker`; добавить отпечаток канонического действия.
4. Отдельно защитить `browser_research_results` от доступа по одному `session_id` при ошибке вышестоящего маршрута; не удалять и не смешивать накопленные данные.
5. Повторно проверить Browser Agent после аварийного завершения Chrome/CDP (Issue #67) и сбросов HTTP/2; эти проблемы независимы от Human Approval.

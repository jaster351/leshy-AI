# Аудит исполняемого контура Browser Approval (07.11.2026)

Статус: **обнаруженный риск, исправление runtime не подтверждено**. Основание: чтение `src/leshy/browser_agent.py` в `main` (`d47bedb3ce570cfc58984a590cf1508542c71cfd`). Это документ статического аудита, а не подтверждение E2E.

## Подтверждённый путь обхода

`BrowserAgent.execute(action, approved=True)` для любого `risk != READ` выставляет `action.arguments["_approval_verified"] = True` и вызывает `adapter.execute(action)`. В этой точке **нет** проверки серверного одноразового grant, owner UUID, session_id, payload hash, срока действия или факта расходования grant. Удаление пользовательского `_approval_verified` перед этим не устраняет проблему: вызывающий код может просто передать `approved=True`.

Дополнительная граница: `BrowserAction.risk` аннотирован как `BrowserRisk`, но dataclass не валидирует тип при создании. Сравнение `action.risk is not BrowserRisk.READ` не является полноценной проверкой доверенной классификации действий. Недопустимо полагаться на классификацию риска, поступившую от модели или клиента: сервер обязан самостоятельно определить уровень риска по операции и её каноническим параметрам.

## Требуемое исправление (fail closed)

1. Для READ разрешать исполнение только после проверки адресной политики; не принимать маркеры подтверждения от клиента.
2. Для MUTATE/COMMIT/FINANCIAL до любого адаптера требовать выданный сервером grant, связанный с проверенным `owner_id`, `session_id`, `action.name`, каноническим URL и неизменяемым hash аргументов. Сумма, валюта, получатель, товар, адрес доставки и метод оплаты — часть hash.
3. Проверять TTL, идентичность и payload непосредственно перед исполнением; атомарно расходовать grant ровно один раз. Любое несовпадение, ошибка хранения или повторное использование — запрет исполнения, без fallback на `approved=True`.
4. Серверный контекст идентичности должен поступать из проверенной Web-сессии или Telegram user_id, а не из полей LLM, request body или query string. Привязка обычного Telegram-пользователя не повышает его до admin.
5. Существующие вызывающие места `approved=True` мигрировать на проверенный серверный контекст. До завершения миграции старые опасные вызовы должны завершаться `ApprovalRequired`/blocked, а не молча исполняться.
6. Не повторять финансовые/commit операции после неопределённого результата адаптера или сетевого timeout; сначала проверять фактический результат по идемпотентному ключу.

## Регрессии, необходимые перед слиянием

- `approved=True` без grant: блокировка для всех трёх опасных рисков.
- Чужой owner/session, неподтверждённая Web-сессия, непривязанный Telegram, истёкший или уже использованный grant: блокировка.
- Изменение URL, суммы, получателя, валюты, аргументов после подтверждения: блокировка.
- Поддельный `_approval_verified` в arguments, поддельный `risk`, прямой вызов адаптера: блокировка.
- Конкурентные два consume одного grant: ровно одно разрешённое исполнение.
- READ без grant продолжает работать в пределах сетевой политики.
- Web, Telegram, API: проверить фактический пользовательский маршрут, а не только отдельный класс.
- Ошибка хранилища подтверждений, рестарт и timeout после COMMIT: fail closed, без повторной покупки.

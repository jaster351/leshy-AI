# SuperAgent Лешего

## Назначение

`SuperAgent` — отдельный управляемый модуль для длительных автономных заданий. Архитектура адаптирует идеи исследовательского прототипа `deepseek-ai/dsh-superagent-prototype`, но использует собственные runtime, SQLite, LLM, поиск, настройки и ограничения Лешего.

Главный принцип: не удерживать пользователя в цикле «спросил → подождал → снова напомнил». Пользователь один раз явно выдаёт задачу, Леший фиксирует разрешённую область работы, выполняет её в фоне и возвращается только с результатом, препятствием или одним действительно блокирующим вопросом.

## Контур выполнения

```text
Trigger → Mandate → Ticket → Assignment → Report
```

- **Trigger** — явная команда пользователя на автономную работу.
- **Mandate** — неизменяемая запись о том, что именно пользователь разрешил сделать. Сам SuperAgent не расширяет область задания.
- **Ticket** — долговечное состояние задачи в SQLite.
- **Assignment** — конкретная попытка выполнения Ticket.
- **Report** — результат попытки: `ready`, `waiting`, `blocked` или `failed`.

## Состояния Ticket

- `queued` — ждёт выполнения;
- `working` — выполняется;
- `waiting` — нужен один конкретный ответ пользователя;
- `ready` — готов результат;
- `blocked` — есть внешнее препятствие;
- `failed` — выполнить не удалось;
- `stopped` — пользователь остановил задачу.

Все Ticket, входные сообщения и Assignment хранятся в основной SQLite-базе `LeshyBrain`. Если процесс завершился во время `working`, при следующем старте такое задание возвращается в очередь, а прерванная попытка помечается как `interrupted`.

## Приоритет ресурсов

SuperAgent использует общий `InferenceScheduler` Лешего с `PRIORITY_BACKGROUND`. Интерактивные Web/Telegram-запросы имеют более высокий приоритет и получают локальную LLM раньше фоновых заданий. Уже начатая генерация не прерывается посередине.

## Команды

Создать автономную задачу:

```text
/agent изучи тему X и подготовь краткий вывод
```

Также поддерживаются `/superagent ...`, `суперагент: ...` и `суперагент ...`.

Управление:

```text
/agent list
/agent status SA-...
/agent stop SA-...
/agent retry SA-...
/agent answer SA-... <ответ на вопрос>
```

Если исполнительу действительно не хватает решения человека, он переводит Ticket в `waiting` и формулирует один конкретный вопрос. Ответ передаётся через `/agent answer ...`, после чего Ticket снова ставится в очередь.

## Интернет и действия

В первой версии SuperAgent может использовать актуальный интернет-поиск Лешего, когда задача требует свежих данных, и затем формировать отчёт локальной LLM. Он не должен притворяться, что выполнил внешнее действие, для которого в текущем контуре нет реально подключённого инструмента.

Опасные действия не получают особых привилегий из-за того, что задача автономная. По мере подключения стандартного `ToolRegistry` Лешего действия с `approval_required` должны продолжать проходить через Human Approval Gate.

## Настройки

Модуль отображается в **Настройки → Модули Лешего → SuperAgent**. Переключение сохраняется в SQLite и применяется без перезапуска. При выключенном модуле команды SuperAgent не перехватываются, а его фоновый worker останавливается.

## Ограничения первой версии

- ограниченный пул независимых фоновых тикетов уже работает параллельно (до 8); генерации на одной локальной модели остаются согласованными через inference-slot;
- внешний произвольный shell/GitHub/OS-control не выдаётся SuperAgent автоматически;
- завершённый результат сохраняется в исходный чат; отдельный realtime push-канал для фонового результата можно развивать независимо от самого durable execution-контракта;
- SuperAgent не создаёт задачи сам по собственной инициативе: требуется явный пользовательский Trigger.

Эти ограничения намеренны: сначала фиксируется надёжный durable execution-контур, затем к нему подключаются дополнительные инструменты без изменения модели Mandate/Ticket/Assignment/Report.

## Долговременные планы (1.10.129)

Для существующего тикета можно отдельно сохранить граф этапов:

```text
/agent plan create SA-... [{"id":"analysis","title":"Изучить код"},{"id":"review","title":"Проверить изменения","depends_on":["analysis"]}]
/agent plan status SA-...
/agent plan pause SA-...
/agent plan resume SA-...
/agent plan cancel SA-...
```

План привязан к владельцу тикета и хранится в `LeshyBrain` SQLite. Отмена основного тикета отменяет связанный план. **Пока это интерфейс хранения и управления этапами:** создание плана не вызывает LLM/OS/Git автоматически и не запускает их исполнение. Для выполнения требуется отдельный доверенный исполнитель, который использует claim/complete с токенами аренды и проверяет права владельца. Это исключает ложные заявления о завершённой разработке.


### Типизированные этапы чтения и аренда исполнителя

План может хранить **необязательный** безопасный инструмент и его аргументы. Пример:

```json
[
  {"id":"version","title":"Определить версию Лешего","tool":"runtime.version","arguments":{}},
  {"id":"knowledge","title":"Найти проверенные сведения",
   "tool":"knowledge.search","arguments":{"query":"архитектура безопасных агентов"},
   "depends_on":["version"]}
]
```

Поддерживаются только `knowledge.search`, `runtime.version` и `runtime.platform`.
Любой `shell.exec`, `workspace.write`, неподтверждённый инструмент,
неверные аргументы или пустой запрос отклоняются **до записи плана**.
Текстовый этап без поля `tool` остаётся *ручным описанием*, а не командой.

Для будущих локальных и доверенных распределённых исполнителей
`SuperAgentPlanBridge.claim(...)` возвращает описание инструмента вместе
с непредсказуемым токеном аренды. `heartbeat(...)` продлевает аренду
только при совпадении токена и владельца и при незавершённом тикете;
после остановки владельцем обновления и завершения запрещены.
Истёкший токен не может подтвердить результат нового исполнителя.

**Важно:** появление данных инструмента и `heartbeat` само по себе **не запускает**
этапы плана. Подключение автоматического локального/кластерного исполнителя
с проверкой прав, контроля ресурсов и подтверждением выполнения — отдельный этап.

### Выполнение разрешённых этапов чтения

Владелец уже созданного плана может явно запустить выполнение подготовленных
безопасных DAG-этапов:

```text
/agent plan run SA-...
/agent plan status SA-...
```

Этот режим использует существующий доверенный CognitiveReadExecutor. Он
атомарно арендует этапы из SQLite, повторно проверяет разрешённые инструменты
перед запуском и обрабатывает максимум 12 этапов за вызов, с максимум 4
независимыми чтениями одновременно. После подтверждения чтения сохраняет
квитанцию и результат либо SHA-256 слишком длинного результата. Успешные
этапы открывают следующие слои графа зависимостей.

Этапы без поля `tool` остаются исключительно ручными описаниями — они не
попадают в пул автоматических исполнителей. Запуск shell, изменение файлов,
управление ОС и браузером через этот маршрут невозможны. Stop/Cancel и
неверный или устаревший токен аренды препятствуют подтверждению результата.
Неуспешный этап не переисполняется в бесконечном цикле одной команды.

**Границы этапа:** команда `/agent plan run` запускает локальные чтения только
по прямому запросу владельца. Непрерывный фоновый исполнитель DAG и выполнение
произвольных действий внутри кластера пока не реализованы; автономный контур
обычных SuperAgent Ticket работает отдельно. Полный Windows end-to-end
не подтверждён.

### Автоматический запуск типизированных чтений (1.10.137)

Чтобы уже созданный план выполнял разрешённые чтения без повторных команд
владельца, нужно один раз явно включить режим:

```text
/agent plan auto SA-...
/agent plan manual SA-...
/agent plan status SA-...
```

- `plan auto` включает сохраняемый в SQLite флаг `auto_run=1`, `plan manual`
  выключает. Для старых и новых планов режим **по умолчанию выключен**.
- После рестарта только лидер SuperAgent просматривает включённые планы
  и планирует доступные типизированные этапы, соблюдая зависимости,
  `max_attempts`, паузу/отмену, owner-bound ticket и аренду.
- Фоновая обработка уступает приоритет обычным заданиям пользователя
  и учитывает доступные ресурсы; параллельно обрабатываются не более
  двух планов, внутри каждого не более четырёх безопасных чтений.
- Текстовые этапы без `tool` остаются **неисполняемыми**, автоматически
  не запускаются shell, RDP, SSH, браузер и изменение файлов/ОС.
- Завершённые/остановленные/заблокированные SuperAgent Tickets не
  запускают новые автоматические действия; временные ошибки откладываются.

Ограничение: это автоматический **read-only** контур, а не произвольный
автономный агент-разработчик. Прежде чем предоставить действия записи или
SSH/RDP, потребуется отдельный контур прав, разрешений и доказательств
выполнения. Windows/PyInstaller/браузерный E2E этой версии ещё не подтверждён.


### Квитанции и проверяемые результаты чтения (1.10.139)

Принцип **evidence before success**: SuperAgent больше не считает DAG-чтение
завершённым лишь потому, что инструмент вернул строку `receipt_id`.
Перед фиксацией шага исполнитель сверяет идентификатор квитанции, инструмент,
успешный статус и SHA-256 реального результата с локальным
`VerifiedToolReceipts`, созданным исполнившимся кодом. Неверный, поддельный
или не соответствующий содержимому результат отклоняется; существующие
ограничения аренды, владельца, паузы и отмены сохраняются.

В **Задачи → Суперагент → Подробнее** после выполнения видны человеческие
итоги: версия, ОС процесса Лешего или число найденных проверенных записей
Knowledge. Технические квитанция, SHA-256 и время доступны через
сворачиваемое «Техническое подтверждение». Пользовательские запросы,
полные тексты записей и URL Knowledge не публикуются в этом списке.
Старые записи без нового формата помечены как исторические, а испорченные
не получают отметку об успешной проверке.

**Границы доверия:** квитанция подтверждает факт выполнения инструмента и
соответствие ответа локальному реестру во время вызова, но **не** истинность
сторонних источников, **не** длительную цифровую подпись аудита и **не**
криптографическую защиту локальной SQLite-базы от администратора.
После перезапуска локальный реестр из памяти процесса не позволяет повторно
проверить подлинность старого `receipt_id`: UI честно говорит «проверено при
выполнении», а не «проверено сейчас». При большом результате сохраняется
его отпечаток с явным сообщением, что полный вывод недоступен.
Полный Windows/E2E в этом проходе не выполнялся.


### Независимая проверка источников Knowledge (1.10.140)

Следующий шаг по идее независимого reviewer: после реального
`knowledge.search` и проверки квитанции ещё один **отдельный детерминированный
исполнитель** анализирует метаданные найденных записей. Он проверяет
наличие корректных HTTP(S)-ссылок, количество различных адресов источников
и дублирование текста. Он не обращается к сети, не исполняет модель и не
запрашивает дополнительных пользовательских полномочий.

Проверка выполняется **до** фиксации успешного шага плана. Неполная или
некорректная структура результата не может пройти как проверенная.
В локальный результат сохраняется только ограниченная сводка без имён сайтов,
полных URL, запросов или текстов Knowledge. При чтении карточки SuperAgent
сводка перепроверяется по сохранённому результату; подменённая сводка не
выдаётся за результат аудита. Если результат усечён, повторная оценка
источников недоступна, что указывается явно.

Web-интерфейс **Задачи → Суперагент → Подробнее** показывает число записей,
записей со ссылками, различных сайтов и повторов. Обозначения «нет ссылок»,
«источников недостаточно» или «ссылки на несколько сайтов» не равны
подтверждению фактов. Ни совпадение источников, ни статус trusted в
локальной базе не заменяют отдельной внешней проверки достоверности.
В этом выпуске **нет** второго LLM-агента, проверки содержимого внешних
веб-страниц или автоматической публикации сведений как истинных.

Дополнительно завершение запущенного шага в приостановленном плане отклоняется
на уровне SQLite. Паузу и отмену нельзя обойти завершением уже взятой аренды.


### Управление доступом к удалённым компьютерам (первый UI-этап)

В разделе **Задачи → SuperAgent → Удалённые компьютеры и разрешения**
владелец с действующей Web-сессией и подтверждённым входом через
провайдера видит **только свои** зарегистрированные узлы и активные
выданные разрешения. Можно нажать **«Отозвать это разрешение»**,
подтвердить действие и сразу увидеть обновлённый список.

Этот экран использует серверный `RemotePermissionPolicy`: факт владения
аккаунтом не берётся из формы, URL, IP или Telegram, а заново проверяется
по серверной Web-cookie и привязке провайдера. После отзыва следующая
проверка полномочий на удалённое действие должна отказать. Для каждого
клиентского запроса не передаются SSH-пароли, ключи или данные других
пользователей. Нет формы выдачи разрешений или регистрации компьютера
по одному IP: владелец должен сначала подтвердить владение узлом.

API: `GET /v1/superagent/remote-access` — строго owner-scoped
инвентаризация, без сетевого подключения; `POST
/v1/superagent/remote-access/revoke` — отзыв одного разрешения с
Same-Origin и `X-Leshy-UI`. В Web UI не требуется вводить UUID и команды.
Пока реализация SSH/RDP не завершена, экран **не подключается к
компьютерам, не запускает SSH и не даёт удалённый рабочий стол**.
Существующие черновые PR с SSH/approval не считаются готовыми.

Добавлены сценарии: неподтверждённый Web-пользователь получает отказ,
чужой узел скрыт, другой пользователь не может отозвать разрешение
владельца, неверное действие/параметры отклоняются, истёкшие разрешения
не показываются. Полная Windows-сборка и браузерный E2E не выполнялись.

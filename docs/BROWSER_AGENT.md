# Browser Agent Лешего

Browser Agent — рабочий слой действий Лешего в интернете. Он не является вторым AI-ассистентом и не заменяет LeshyBrain: личность, память, диалог и выбор цели остаются в ядре Лешего.

## Что реализовано

Рабочая цепочка: `LeshyBrain -> BrowserPlatform -> BrowserAgent -> Browser Use / Playwright -> браузер`.

- **Browser Use** выполняет семантическое исследование сайтов и динамические браузерные задачи.
- **Playwright** выполняет детерминированные workflow и остаётся фундаментом существующих browser-skills.
- **LeshyBrowserUseLLM** подключает родную локальную `LLM.chat()` Лешего к Browser Use без обязательного OpenAI/Ollama или другого платного API.
- Системный Edge/Chrome/Chromium используется с отдельным профилем Лешего и сохранением browser state.
- Естественные запросы о товарах, билетах, гостиницах и бронированиях маршрутизируются в Browser Platform.
- Последние найденные варианты сохраняются в LeshyBrain SQLite и восстанавливаются после перезапуска.
- Web UI показывает одноразовое подтверждение перед внешним обязательством или оплатой.

Первое сообщение вида «купи iPhone» или «забронируй отель» **не совершает покупку**. Леший сначала ищет и сравнивает варианты. После выбора (`купи первый`, `забронируй вариант 2`) создаётся отдельное подтверждение.

## Human Approval Gate

Действия делятся на уровни риска:

- `read` — поиск, чтение, сравнение: может выполняться автоматически;
- `mutate` — изменение данных: требует подтверждения;
- `commit` — заказ, бронирование, публикация и другое внешнее обязательство: требует подтверждения;
- `financial` — списание денег: отдельное явное подтверждение, включая сумму и валюту.

Approval одноразовый, привязан к владельцу и действует ограниченное время. Он намеренно не сохраняется на диск: после перезапуска старое разрешение невозможно повторно использовать. При этом результаты поиска сохраняются, поэтому пользователь может снова выбрать найденный вариант после рестарта.

Browser Use дополнительно проверяет соответствие имени команды и уровня риска (`agent_read`/`research` → `read`, `agent_mutate` → `mutate`, `agent_commit` → `commit`, `agent_financial` → `financial`). Команда оплаты, переданная как `read`, блокируется до запуска backend. Это защита от ошибочной классификации, **не замена** проверки подлинности approval и не гарантия контроля редиректов.

Browser Use получает внутренний `_approval_verified` только после прохождения Human Approval Gate. Финансовый адаптер дополнительно требует `approval_summary`; изменение суммы, валюты, получателя, количества или дополнительных услуг после подтверждения запрещено.

### Технический read-only

Для `read` ограничение реализовано не только инструкцией LLM. Browser Use запускается с отдельным `Tools(exclude_actions=...)`: отключены `click`, `input`, `send_keys`, `select_dropdown`, `evaluate`, upload и локальные операции чтения/записи файлов. Остаются безопасные действия навигации, поиска, прокрутки и извлечения. После подтверждённого `commit/financial` взаимодействие с формами разрешается, но произвольный JavaScript и файловый I/O остаются отключены.

## Доменная изоляция и CAPTCHA

Browser Use и Playwright получают allowlist доменов. Явный allowlist нельзя автоматически расширить стартовым URL. Переход/редирект за его пределы блокируется.

CAPTCHA, challenge и 2FA не обходятся скрытно. Browser Agent останавливается и возвращает управление человеку.

Пароли, cookies, CVV, токены и другие секреты нельзя включать в публичные approval-данные и диагностический результат. Browser state хранится в отдельном каталоге LeshyBrain с ограниченными правами там, где ОС их поддерживает.

### Проверка URL до вызова адаптера

BrowserAgent принимает только абсолютные HTTP/HTTPS URL с корректным hostname. Встроенные credentials (`user:password@`), нестандартные порты, а также `file:`, `javascript:`, `ftp:` и некорректные URL блокируются до вызова браузерного адаптера даже при пустом allowlist. Разрешены стандартные порты 80 для HTTP и 443 для HTTPS. Это ограничение верхнего уровня; браузерные редиректы и навигация дополнительно должны контролироваться внутри адаптера. Исключение для нестандартного порта допускается только на loopback-хостах `127.0.0.1`, `::1`, `localhost`, когда соответствующий хост **явно** включён в allowlist. Это сохраняет локальный Browser E2E на случайном порту, но не разрешает произвольные внешние порты.

## Web API

Runtime `web_server_impl8` добавляет защищённые API:

- `GET /v1/browser/approvals` — ожидающие подтверждения;
- `POST /v1/browser/approvals/resolve` — одноразовое подтвердить/отменить;
- `POST /v1/documents/convert` — локальный Document Intelligence;
- `GET /v1/tools/extensions` — установленные MCP/Skills;
- `POST /v1/tools/extensions/inspect` — просмотр разрешений до установки;
- `POST /v1/tools/extensions/install` — подтверждённая изолированная установка;
- `POST /v1/tools/extensions/uninstall` — подтверждённое удаление;
- `POST /v1/tools/call` — вызов зарегистрированного MCP tool.

`browser-approval-panel.js` показывает в Web UI кнопки `Подтвердить` / `Отмена`, а для финансового действия — отдельное `Подтвердить оплату`.

## MCP / Skills Marketplace

`ToolRegistry` хранит манифесты локально. Опасные permissions (`mutate`, `desktop`, `secrets`, `financial`) требуют approval до вызова tool.

`ExtensionMarketplace` ставит Python MCP-расширение в отдельный venv. Marketplace требует закреплённую версию пакета, HTTPS-ссылку на исходный репозиторий и указанную лицензию. После установки сервер обязан успешно объявить MCP tools; иначе установка откатывается.

Существующий Marketplace Лешего остаётся пользовательским каталогом plugins/skills. MCP Tools Gateway является его безопасным исполнительным контуром для стандартных MCP-инструментов, а не вторым AI-ассистентом.

## Document Intelligence

`DocumentIntelligence` использует MarkItDown для PDF/DOCX/XLSX/PPTX и поддерживаемых текстовых форматов. Обработка локальная; удалённый URL не принимается как путь к документу. Для PDF предусмотрен fallback через pypdf, для простых текстовых форматов — встроенный reader.

## Computer Use

В Лешем уже имеется отдельный `ComputerUseController` и адаптеры наблюдения/действий desktop UI. В настройках он теперь представлен самостоятельным модулем `computer-use`; Browser Agent не подменяет Computer Use.

## Отказоустойчивость

Если Browser Use не может выполнить read/research, BrowserAgent может перейти к следующему совместимому адаптеру, а исследовательский сценарий сохраняет результаты обычного live search. Отсутствие Browser Use/MCP не должно ломать общий чат.

Streaming-маршрут всегда снимает request из реестра активных запросов через `finally`, включая отмену и исключение.

## Проверки

Regression-набор покрывает:

- поиск сначала, а не немедленную покупку;
- `купи iPhone` без слова «товар» как research-first сценарий;
- выбор первого/второго/третьего варианта;
- восстановление выбранных вариантов после перезапуска BrowserPlatform;
- необходимость суммы для оплаты;
- owner-bound и одноразовый approval;
- отсутствие секретных arguments в публичном approval;
- запрет non-read Browser Use без approval;
- запрет финансового действия без approval summary;
- физическое отсутствие mutating tools в read-only Browser Use registry;
- запрет расширения явного доменного allowlist стартовым URL;
- локальный Document Intelligence и запрет URL;
- сохранение/выключение MCP manifest;
- запрет небезопасного удалённого HTTP MCP;
- обязательное подтверждение dangerous MCP tool;
- обязательное подтверждение установки расширения;
- синтаксис Browser Approval/Marketplace/Module Settings JavaScript в CI.

Реальные платежи не используются в CI. Финальный E2E финансового действия проверяется на тестовом/песочном сценарии без списания денег.


## Изоляция браузерных профилей по владельцу

В маршрутах BrowserPlatform операции исследования, открытия URL и подтверждённые внешние действия передают `profile_namespace=owner` и стабильный SHA-256 идентификатора владельца как `profile_key`. Это исключает общий каталог cookies для разных `owner_id` в этих маршрутах и сохраняет профиль одного владельца между исследованиями и подтверждениями. Сырой идентификатор владельца в имени каталога не сохраняется. Пустой owner отклоняется.

Ограничение: изоляция зависит от корректной аутентификации и назначения `owner_id` вызывающим Web/Telegram маршрутом. Старый fallback `web:local` сам по себе не является безопасной идентификацией разных пользователей; его следует отдельно устранить в многопользовательском Web-контуре. Другие прямые вызовы BrowserUseAdapter ещё требуют аудита. Это изменение не заменяет проверку Human Approval Gate и защиту переходов/редиректов.


## Защита внутреннего маркера подтверждения

`BrowserAgent.execute()` удаляет любой входной `_approval_verified` из
`BrowserAction.arguments` перед передачей действия адаптеру. Для действий
`READ` маркер никогда не передаётся. Для изменяющих действий маркер
устанавливается только после прохождения существующего параметра
`approved=True`; неподтверждённое действие вызывает `ApprovalRequired`.
Исходный объект `BrowserAction` не изменяется.

Это дополнительная защита от подстановки маркера через аргументы модели/API,
**не** полноценная криптографическая авторизация. Параметр `approved=True`
пока остаётся доверенным и должен вызываться только серверным маршрутом после
проверки одноразового разрешения, привязанного к владельцу, сессии и действию.
Прямые вызовы адаптера и безопасность перенаправлений требуют отдельной защиты.

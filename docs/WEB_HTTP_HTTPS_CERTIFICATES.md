# HTTP, HTTPS и сертификаты Лешего

Задача #301, ответственный Codex, ветка `codex/301-http-https-certificates`. База main: `a5bb4215cb4fd5e1ae3ac66f5be84349a103cfda`. Это реализация для review; настоящий сертификат, доступ из Интернета и автоматическое продление пока не проверены.

## Порты и запуск

HTTP сохраняет порт 8765 по умолчанию. HTTPS использует отдельный порт 8766 и ожидает установки сертификата. Оба listener используют один экземпляр приложения, один обработчик и существующие фоновые задачи. Ошибка bind одного протокола отображается в состоянии и не мешает запустить другой; отсутствие любого доступного listener останавливает запуск.

В настройках подтверждённого хозяина сервера доступны включение HTTP/HTTPS, отдельные порты 1–65535 и имя сервера для проверки сертификата. Порты должны различаться; хотя бы один протокол остаётся включённым. Для сохранения режима только HTTPS уже нужен действующий сертификат, покрывающий указанное имя. Изменение портов применяется после перезапуска приложения; интерфейс показывает различие сохранённых и применённых параметров. Самопроизвольного перехода браузера на новый адрес нет.

Приоритет HTTP-порта: явный `--port`, затем `LESHY_PORT`, затем сохранённое значение, затем 8765. Для HTTPS `LESHY_HTTPS_PORT` перекрывает сохранённое значение. Windows launcher использует тот же порядок, не подставляет 8765 как якобы явный CLI-аргумент и открывает HTTP либо сохранённое HTTPS-имя в режиме только HTTPS.

Доступ к маршрутам управления проверяет Telegram-сессию и хозяина конкретного экземпляра сервера. Глобальная роль создателя сама по себе не даёт прав менять чужой сервер. Запись требует точного Origin, `X-Leshy-UI: network-security`, JSON ограниченного размера и подтверждения. Разные протоколы имеют отдельные cookie: HTTPS — Secure с префиксом `__Host-`. Непроверенный `X-Forwarded-Proto` не создаёт TLS; режим доверенного reverse proxy здесь не добавлен.

## Импорт купленного или собственного сертификата

В панели выбираются PEM-сертификат с цепочкой, соответствующий PEM-ключ и при необходимости пароль ключа. Ограничения файлов: 256 КБ для цепочки, 64 КБ для ключа. Закрытый ключ принимается только по реальному HTTPS либо при локальном клиенте и локальном Host. Удалённый HTTP не разрешает импорт ключа.

Проверяются соответствие ключа, минимальная длина RSA/EC, срок каждого сертификата цепочки, порядок и подписи issuer, CA/path length/key usage промежуточных сертификатов, EKU serverAuth и SAN с различением DNS/IP. SSLContext TLS 1.2+ создаётся до сохранения. Эти проверки не доказывают доверие цепочке на телефоне или доверенность произвольного корня.

Сертификат и ключ сохраняются одной записью существующего secret_store: DPAPI текущего Windows-пользователя, защищённые ACL; на POSIX — ограниченные права каталога/файла. Symlink/reparse в служебных путях отклоняются. Временные PEM нужны для стандартного `SSLContext.load_cert_chain` и удаляются после загрузки. Ключи и пароли не возвращаются через API.

После успешной записи новые TLS-соединения получают новый контекст, уже открытые соединения не обрываются. При ошибке записи прежние сертификат и контекст остаются. Ручная установка отзывает старые ACME jobs перед commit. При неудачном commit параметры продления откатываются; если job уже выполнялся, его неизвестный результат сохраняется и автоматический повтор запрещён. Сбой диска, мешающий записать сам откат, требует ручной проверки состояния перед перезапуском.

## Бесплатный выпуск и продление

Собственный ограниченный клиент RFC 8555 использует имеющуюся cryptography и стандартный HTTPS-клиент, без новых зависимостей. Поддерживаются DNS-имена и HTTP-01, фиксированные staging/production Let's Encrypt. Wildcard, DNS-01 и профиль выдачи сертификатов для IP здесь не реализованы. Для IP можно импортировать подходящий сертификат.

1. Указать публичные домены, email и среду. «Сохранить параметры / получить условия» читает действующие условия выбранного центра.
2. Прочитать условия и подтвердить согласие на них и передачу доменов/email выбранному центру. Согласие привязано к точным параметрам и URL условий.
3. Проверить DNS и доступность HTTP-01 по внешнему порту 80. При другом HTTP-порте приложения нужно настроенное владельцем перенаправление. Леший не меняет роутер, firewall, UAC или права ОС.
4. Нажать «Получить и установить сертификат». Первый выпуск не начинается от простого сохранения настроек. Результат отображается после фактического завершения job. Staging не даёт браузерно доверенный сертификат.
5. Для продления включить соответствующий флажок. Планировщик работает только пока запущен Леший, проверяет срок раз в минуту и не создаёт отдельную службу Windows или системное задание.

Запросы CA ограничены своим HTTPS-origin, временем и размером; redirects и системный proxy отключены. Ключ аккаунта сохраняется защищённо. Retry-After не сокращается до преждевременного polling; общий deadline и отмена ограничивают ожидание. Автоматический повтор допустим только при явном badNonce протокола.

Потерянный ответ POST, остановка или изменение параметров во время выпуска оставляют `outcome_unknown`. Отключение и повторное включение либо новый scope не очищают этот маркер. Новый выпуск требует проверки прежнего результата владельцем и отдельного подтверждения. Определённая ошибка также приостанавливает автопродление, но допускает обычный явный ручной повтор. При изменении Terms UI получает новую ссылку и запрашивает новое согласие, не начинает выпуск со старым.

## Связь с голосовым UI

Браузерный микрофон при удалённом доступе требует доверенного HTTPS; обычный HTTP остаётся для доступных без микрофона функций. Заголовок `X-Leshy-UI: voice` не является аутентификацией. Если настроен `LESHY_API_TOKEN`, cookie не обходит bearer gate. Иначе Web-запрос голоса должен иметь действующую серверную сессию и точный Origin. Изменения голоса и анимированного круга находятся отдельно в #271; новый WSS-транспорт здесь не вводится.

## Проверки и ограничения

Фактически пройдены семь тестов `tests/test_web_transport_security.py` по явному разрешению владельца: настройки и приоритет портов; различение DNS/IP SAN; несоответствие ключа; минимальный срок цепочки; запрет non-CA issuer; откат при ошибке записи и удаление временных PEM. Тесты использовали синтетические сертификаты, временное хранилище и блокировку внешних socket.connect. Это проверка helper, а не сервера целиком.

Выполнены синтаксические AST/JS-проверки без запуска кода, read-back и дополнительное статическое cross-review подагентами Codex. Найденные ошибки consent/unknown, import rollback и независимого bind исправлены. Это не независимое Review-by-ChatGPT.

`tests/test_web_acme_lifecycle.py` содержит отдельные регрессии ACME и bind с подменой CA/потоков/сокетов. Они не запускались: разрешение владельца относится только к первоначальным семи тестам другого файла. Новые проверки требуют отдельного явного разрешения по AGENTS.md.

Не выполнялись: выпуск и отзыв настоящего сертификата, внешний HTTP-01, реальные listeners, перезапуск Windows launcher, PyInstaller, автоматическое продление, доверие браузера, голос/микрофон, Android/iOS/Windows E2E, общая тестовая suite и GitHub Actions. До независимого ревью и разрешённой сквозной проверки PR остаётся draft.

Для ручной приёмки нужны DNS/домен, реальная схема внешних портов и авторизованная установка. Проверять сначала staging: новый выпуск, обновлённые Terms, потери ответов, отмену, занятый порт каждого протокола, HTTP/HTTPS вход по отдельности, неверные PEM, отказ записи, истечение промежуточного сертификата, перезапуск и замену сертификата при активном TLS. Лишь затем разрешённая проверка production и микрофона по доверенному HTTPS.

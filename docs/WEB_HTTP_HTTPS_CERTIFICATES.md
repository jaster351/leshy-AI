# HTTP, HTTPS и сертификаты Лешего

Задача #301, ответственный Codex, ветка `codex/301-http-https-certificates`. Основа main `9bf078814c721771227f574c583f0427310bab2f` (1.10.191); последующая main `b4bfd27faa3535ef9a77b6ffe5dc4e43e49f27b4` меняет только log/README.md и проверена отдельно. Это реализация для review; настоящий сертификат, доступ из Интернета и автоматическое продление пока не проверены.

## Порты и запуск

Оба документированных entry point — `windows/launcher.py` и `packaging/launcher.py` — передают HTTP-порт только при явном `--port`; иначе сохраняются приоритет `LESHY_PORT` и сохранённые настройки. По умолчанию host `auto`, явный `--host`/env не расширяется. Браузер получает URL от фактически запущенного listener: универсальный launcher больше не открывает hardcoded HTTP/8765 по таймеру до bind. ManagedBrowser создаётся лениво после готовности и закрывается владельцем launcher; поздний callback после завершения не открывает новое окно.

HTTP сохраняет порт 8765 по умолчанию. HTTPS использует отдельный порт 8766 и ожидает установки сертификата. Оба listener используют один экземпляр приложения, один обработчик и существующие фоновые задачи. Ошибка bind одного протокола отображается в состоянии и не мешает запустить другой; отсутствие любого доступного listener останавливает запуск.

Уточнение владельца: интерфейс должен открываться по любому IP сервера и любому домену, направленному DNS на сервер. Режим привязки по умолчанию — `auto`: отдельные IPv4 `0.0.0.0` и IPv6 `::` для каждого протокола, с явным `IPV6_V6ONLY=1` до bind. Это исключает двойной приём IPv4 и работает при отсутствии dualstack socket. Недоступное семейство и занятые адреса показаны по отдельности; успешная соседняя привязка продолжает работу. Явный `--host`/`LESHY_HOST` ограничивает привязку указанным IP или адресами этого имени, без расширения до wildcard. Параметры DNS, NAT, маршрутизатора и firewall остаются ответственностью администратора; код не может принять пакет, который сеть не доставляет этому серверу.

`0.0.0.0`/`::` — адреса привязки, для браузера используются localhost, действительный IP интерфейса или домен. Обычный HTTP не имеет фиксированного Host allowlist; Origin проверяется относительно фактического Host/порта текущего запроса, cookie остаётся привязанной к конкретному имени. Поле hostname в настройках — каноническое имя сертификата/локального открытия, а не запрет других доменов. HTTPS aliases/IP должны присутствовать в SAN действующего сертификата; один multi-SAN сертификат допустим, универсальный доверенный сертификат для произвольных имён не обещается.

При accept IPv4-mapped IPv6 peer нормализуется в обычный IPv4 до существующих local guards. Forwarded-заголовки не заменяют фактический peer. Приватный импорт ключа по HTTP по-прежнему ограничен loopback peer и localhost/loopback Host. На Windows `SO_REUSEADDR` отключён и до bind выставляется `SO_EXCLUSIVEADDRUSE`; при ошибке не применяется небезопасный fallback. Это не меняет firewall/UAC.

В настройках подтверждённого хозяина сервера доступны включение HTTP/HTTPS, отдельные порты 1–65535 и имя сервера для проверки сертификата. Порты должны различаться; хотя бы один протокол остаётся включённым. Для сохранения режима только HTTPS уже нужен действующий сертификат, покрывающий указанное имя. Изменение портов применяется после перезапуска приложения; интерфейс показывает различие сохранённых и применённых параметров. Самопроизвольного перехода браузера на новый адрес нет.

Приоритет HTTP-порта: явный `--port`, затем `LESHY_PORT`, затем сохранённое значение, затем 8765. Для HTTPS `LESHY_HTTPS_PORT` перекрывает сохранённое значение. Windows launcher использует тот же порядок и не подставляет 8765 как якобы явный CLI-аргумент. Адрес для браузера передаётся callback после запуска listener: сначала работающий HTTP, затем работающий HTTPS с действующим сертификатом для указанного имени. При занятом HTTP-порте launcher не открывает находящийся на нём чужой сервис. Если подходящий адрес не подтверждён, автоматического открытия нет.

Из свежей main сохранены ManagedBrowser, tray, --no-tray/--scheduled-start, ручной stop marker, frozen-логи и cleanup. Даже --no-browser получает фактический ready URL для последующего пункта трея «Открыть»; только автоматическое открытие отключено. Runtime регистрируется целиком, shutdown() выставляет сигнал остановки, основная finally закрывает все IPv4/IPv6 listeners. Ранняя остановка из трея не должна запускать ещё не готовый сервер.

LAN cluster получает кандидата endpoint из живых привязок через app.web_security до создания handler, а не фиксированный HTTP/IPv4 URL. Сохраняется явный LESHY_CLUSTER_ADVERTISE владельца. Для HTTPS используется имя, покрытое сертификатом; DNS/сеть и доверие CA у соседей не объявляются проверенными. Если подходящего входящего endpoint нет, локальные вычисления сохраняются, а подписанная публичная копия профиля сообщает accepting_tasks=false. Новые узлы могут принимать такой профиль для Telegram election/CreatorConsensus без выбора удалённым исполнителем. Старые узлы могут игнорировать профиль без endpoint; это граница совместимости до настройки пригодного адреса. cluster_orchestrator.py и требования моделей из #175 не меняются.

Репликация общих знаний сохраняет отдельную существующую границу LAN-IP: DNS endpoints и пассивные профили пропускаются до чтения курсора и HTTP-запроса, с явным статусом unsupported_targets/причинами, без ложного успешного обмена и без бесконечных ошибок. Подходящие LAN-IP соседи продолжают прежний путь. Cluster tasks по HTTPS/DNS и Web UI по домену не доказывают поддержку DNS-репликации; безопасный DNS-pinned транспорт для неё здесь не реализован. Личная память и правила экспорта знаний не меняются.

Перед записью учитываются переопределения текущего запуска: например, при `--port 8765` нельзя сохранить HTTPS 8765, даже если сохранённый HTTP равен 9000. Иначе effective-конфигурация следующего запуска получила бы одинаковые порты. Панель отдельно показывает наличие переопределения; одно изменение сохранённого порта его не отменяет. Отказ до записи покрыт отдельно разрешёнными изолированными проверками guard; это не проверка настоящего перезапуска Windows.

HTTP-01 в этой реализации требует включённого и работающего HTTP listener Лешего, а также настроенного владельцем доступа к нему через внешний порт 80. Перед отключением HTTP нужно закончить текущий выпуск и отключить автопродление. Эта проверка атомарна относительно ACME configure/job (порядок блокировок ACME → core); включение автопродления и начало выпуска также проверяют транспорт до обращения к CA. Произвольная схема reverse proxy, пересылающая HTTP-01 в HTTPS-only backend, здесь не поддерживается.

Режим только HTTPS с вручную установленным сертификатом требует локального способа восстановления: при просроченной цепочке приложение не запускает недоверенный TLS или обычный HTTP автоматически. Для восстановления хозяин на сервере останавливает приложение, делает защищённую резервную копию `web-security/transport.json` внутри своего brain_dir и локально задаёт `http_enabled: true` с отдельным свободным HTTP-портом. Затем запускает Лешего с `--host 127.0.0.1 --port <этот порт>`, входит подтверждённым хозяином через localhost и устанавливает новый сертификат. После проверки возвращает нужные параметры. Ключи, хранилище сертификатов и память при этом удалять не требуется. Этот ручной recovery описан, но на реальной установке не выполнялся.

Доступ к маршрутам управления проверяет Telegram-сессию и хозяина конкретного экземпляра сервера. Глобальная роль создателя сама по себе не даёт прав менять чужой сервер. Запись требует точного Origin, `X-Leshy-UI: network-security`, JSON ограниченного размера и подтверждения. Разные протоколы имеют отдельные cookie: HTTPS — Secure с префиксом `__Host-`. Непроверенный `X-Forwarded-Proto` не создаёт TLS; режим доверенного reverse proxy здесь не добавлен.

## Импорт купленного или собственного сертификата

В панели выбираются PEM-сертификат с цепочкой, соответствующий PEM-ключ и при необходимости пароль ключа. Ограничения файлов: 256 КБ для цепочки, 64 КБ для ключа. Закрытый ключ принимается только по реальному HTTPS либо при локальном клиенте и локальном Host. Удалённый HTTP не разрешает импорт ключа.

Проверяются соответствие ключа, минимальная длина RSA/EC, срок каждого сертификата цепочки, порядок и подписи issuer, CA/path length/key usage промежуточных сертификатов, EKU serverAuth и SAN с различением DNS/IP. SSLContext TLS 1.2+ создаётся до сохранения. Эти проверки не доказывают доверие цепочке на телефоне или доверенность произвольного корня.

Сертификат и ключ сохраняются одной записью существующего secret_store: DPAPI текущего Windows-пользователя, защищённые ACL; на POSIX — ограниченные права каталога/файла. Symlink/reparse в служебных путях отклоняются. Временные PEM нужны для стандартного `SSLContext.load_cert_chain` и удаляются после загрузки. Ключи и пароли не возвращаются через API.

После успешной записи новые TLS-соединения получают новый контекст, уже открытые соединения не обрываются. При ошибке записи прежние сертификат и контекст остаются. Ручная установка отзывает старые ACME jobs перед commit. При неудачном commit параметры продления откатываются; если job уже выполнялся, его неизвестный результат сохраняется и автоматический повтор запрещён. Сбой диска, мешающий записать сам откат, требует ручной проверки состояния перед перезапуском.

## HTTPS по IP без домена: локальный CA

Первоначальную настройку выполняет подтверждённый хозяин через localhost **на самом сервере** или уже доверенный HTTPS. Localhost другого компьютера и forwarded-заголовки не дают разрешение. Удалённый HTTP не используется для создания CA, скачивания корня и передачи закрытых ключей.

1. На сервере сохранить отдельные HTTP/HTTPS-порты, включённый HTTPS и основное IP/имя сервера. Первоначально оставить доступный HTTP для локального восстановления. Изменение портов требует перезапуска.
2. В «HTTPS по IP без домена» указать до 32 IP и имён без схемы/порта, по одному на строку. Основное имя из настроек должно входить в список SAN. Приватные IPv4/IPv6 допустимы; `0.0.0.0`, `::`, wildcard, multicast и зона link-local отклоняются.
3. Прочитать пояснение о корневом доверии, подтвердить область и нажать выпуск. Создаются EC P-256 корень на 10 лет и leaf на 30 дней с указанными SAN. Внешнего CA и передачи доменов/email здесь нет.
4. Скачать `Leshy-local-root.cer`. UI получает DER через owner API, проверяет SHA-256 и передаёт файл браузеру. Проверить сохранение файла. Сверить отпечаток с сервером через отдельный доверенный канал и передать публичный корень на свои устройства. Закрытый ключ для этого не нужен и API его не экспортирует.
5. Установить доверие корневому CA средствами каждого устройства: Windows — нужная область пользователя и доверенные корневые центры; Android — управление сертификатами в настройках безопасности с учётом версии/производителя; iOS/iPadOS — установка профиля и отдельное включение полного SSL/TLS-доверия. Леший не делает это автоматически. Проверить HTTPS в браузере без обхода предупреждений, затем разрешение микрофона и полный разговор.

Доверенный корневой CA удостоверяет сертификаты, подписанные его ключом: защищать нужно именно ключ сервера. Корень не ограничен текущими IP через NameConstraints; добавление адреса не меняет установленный корень, но требует явного выпуска новых SAN. Отключение продления не снимает доверие на устройствах и не отзывает уже выданный сертификат. Доверие снимается средствами устройства.

Корень неизменно хранится в `web-security/local-ca-authority.secret`, профиль — в `local-ca.json`, с существующей защитой каталога/secret_store (DPAPI Windows, права на POSIX). Повреждённый профиль либо утрата/повреждение известного корня блокируют выпуск без молчаливой ротации. Отсутствующий профиль не возобновляет продление; новый явный выпуск может использовать только сохранённый исходный корень. Не удалять эти файлы для «сброса ошибки»: это теряет исходную личность CA. Восстанавливать защищённую резервную копию на сервере, затем проверять отпечаток.

Продление проверяется раз в минуту и начинается за 7 дней до истечения при работающем приложении и сохранённом согласии. После долгого выключения собственный leaf проверяется до bind, чтобы HTTPS-only мог восстановиться. Проверяются прежний root, SAN и fingerprint установленного leaf; активный ACME не допускает локального продления. Чужой сертификат, ошибка профиля, остановка или неоднозначная установка переводят режим в attention без автоматического повтора. Истечение корня требует отдельной замены доверия владельцем. Реальные продление и HTTPS-only recovery ещё не проверены.

Ручной импорт и настройка ACME отключают локальное продление; локальный выпуск отключает ACME с сохранением неизвестного результата прежнего заказа. При исключении и неизменившемся сертификате параметры откатываются. Ошибка чтения Terms, сохранённая ACME как `error` без исключения, оставляет local renewal выключенным: проверить состояние в панели. Порядок блокировок ACME → local CA → core; workers стартуют/останавливаются вне core.

Доверие браузера не доказывает доверие нативного Android-клиента: приложения с современным target API по умолчанию не доверяют пользовательскому CA. Для приложения нужна отдельная настройка доверенного корня и привязки сервера; обход TLS здесь не добавляется.

Официальные инструкции: [хранилища Windows](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/inspect-certificates-manage-certificate-stores), [сертификаты Android](https://support.google.com/pixelphone/answer/2844832?hl=en), [SSL/TLS-доверие iOS/iPadOS](https://support.apple.com/en-ug/102390), [доверенные CA Android-приложения](https://developer.android.com/privacy-and-security/security-config). Конкретные устройства и браузеры ещё не проверялись.

## Let's Encrypt: бесплатный выпуск и продление для домена

Собственный ограниченный клиент RFC 8555 использует имеющуюся cryptography и стандартный HTTPS-клиент, без новых зависимостей. Поддерживаются DNS-имена и HTTP-01, фиксированные staging/production Let's Encrypt. Wildcard, DNS-01 и профиль выдачи сертификатов для IP здесь не реализованы. Для IP можно импортировать подходящий сертификат.

1. Указать публичные домены, email и среду. «Сохранить параметры / получить условия» читает действующие условия выбранного центра.
2. Прочитать условия и подтвердить согласие на них и передачу доменов/email выбранному центру. Согласие привязано к точным параметрам и URL условий.
3. Проверить DNS и доступность HTTP-01 по внешнему порту 80. При другом HTTP-порте приложения нужно настроенное владельцем перенаправление. Леший не меняет роутер, firewall, UAC или права ОС.
4. Нажать «Получить и установить сертификат». Первый выпуск не начинается от простого сохранения настроек. Результат отображается после фактического завершения job. Staging не даёт браузерно доверенный сертификат.
5. Для продления включить соответствующий флажок. Планировщик работает только пока запущен Леший, проверяет срок раз в минуту и не создаёт отдельную службу Windows или системное задание.

Запросы CA ограничены своим HTTPS-origin, временем и размером; redirects и системный proxy отключены. Ключ аккаунта сохраняется защищённо. Retry-After не сокращается до преждевременного polling; общий deadline и отмена ограничивают ожидание. Автоматический повтор допустим только при явном badNonce протокола.

Потерянный ответ POST, остановка или изменение параметров во время выпуска оставляют `outcome_unknown`. Отключение и повторное включение либо новый scope не очищают этот маркер. Новый выпуск требует проверки прежнего результата владельцем и отдельного подтверждения. Определённая ошибка также приостанавливает автопродление, но допускает обычный явный ручной повтор. При изменении Terms UI получает новую ссылку и запрашивает новое согласие, не начинает выпуск со старым.

## Связь с голосовым UI

Браузерный микрофон при удалённом доступе требует доверенного HTTPS; обычный HTTP остаётся для доступных без микрофона функций и не обеспечивает конфиденциальность сессии. HTTPS использует отдельную `__Host-` Secure cookie; HTTP-cookie не принимается как HTTPS-сессия. Заголовок `X-Leshy-UI: voice` не является аутентификацией. Если настроен `LESHY_API_TOKEN`, cookie не обходит bearer gate; постоянный bearer принимается только по настоящему TLS либо от loopback peer с loopback Host. Иначе Web-запрос голоса должен иметь действующую серверную сессию и точный Origin. Изменения голоса и анимированного круга находятся отдельно в #271; новый WSS-транспорт здесь не вводится.

До включения нового guard необходимо интегрировать актуальный #307: он обновляет заголовки существующих voice-live, примера голоса и «Прочитать вслух» в message-actions.js. Иначе прежний caller получит 403. Это явная зависимость исполняемых маршрутов; независимость файлов двух PR не означает независимость порядка их внедрения.

## Проверки и ограничения

Дополнение после 6474c07: добавлены local CA/runtime/UI и исправления двух замечаний Review-by-ChatGPT о bearer по HTTP и deadline чтения ACME. Новые изолированные сценарии пока подготовлены только исходниками, не запускались. ## Уточнения проверки готовности и безопасности 20.11.2026

Порт и живой worker сами по себе не подтверждают работу Web. Перед browser callback каждый listener получает ограниченную внутреннюю HTTP(S)-пробу собственного /v1/web-ready: случайный nonce и HMAC с отдельным секретом этой привязки, без cookie, bearer и пользовательского запроса. Используется числовой адрес привязки, wildcard проверяется по loopback без DNS/proxy. Для HTTPS включены CERT_REQUIRED и проверка имени, доверие ограничено публичной цепочкой установленного сертификата, затем проверяется точный leaf fingerprint до GET. Это проверка своего handler, а не удалённого доступа, публичного TCP80 или доверия телефона. Ошибка ответа, неверный MAC, framing, срок или остановка не открывают браузер и не выставляют ready. Новый сертификат сбрасывает ready до следующей пробы.

В status отдельно видны listening/ready; панель отличает открытый порт от подтверждённого ответа. ACME требует готовый внутренний HTTP handler, но http01_public_port_80_verified остаётся false: внешний DNS/NAT/firewall не проверяются этой пробой. Удалённый HTTP voice запрещён и для bearer, и для cookie; UI HTTP сохраняется, удалённый микрофон требует доверенный HTTPS.

На один HTTP/HTTPS listener допускается не более32 обслуживаемых соединений: слот берётся без ожидания до запуска worker и удерживается до завершения handler, включая TLS handshake и чтение тела. При насыщении новое соединение закрывается; start/handshake/handler error освобождает слот. Это не глобальный лимит приложения и не полная защита всех сетевых протоколов. Для JSON административных /v1/web-security/ тело читается порциями с одним monotonic deadline10 секунд, не более512КБ; timeout даёт408 и закрытие соединения, неполное тело также закрывает соединение. Остальные Web endpoints и чтение заголовков этим deadline не охватываются.

Leaf с BasicConstraints CA:TRUE отклоняется. Локальная validation описывает ключ/SAN/сроки и подписи соседних сертификатов; доверенный root anchor и доверие ОС/браузера не подтверждаются. CN нового локального CA сокращён до Leshy Local CA, чтобы не превышать64 UTF-8 байта.

# Граница доверия Browser Agent и одноразовые подтверждения

Статический аудит 2026-11-04. Базовый `main`: `8ee6076922a5b411d4d82de47b1a3cf3c2d009ef`.

## Подтверждённые наблюдения

- `src/leshy/browser_platform_runtime.py`: `BrowserPlatform.resolve_approval()` получает действие из `approvals.consume(owner_id, approval_id)` и вызывает `agent.execute(action, approved=True)`. Проверка хранилища подтверждений является критической границей доверия.
- `src/leshy/browser_use_adapter.py`: для изменяющих действий проверяется булевый аргумент `_approval_verified`. Сам по себе флаг из `action.arguments` не является доказательством подтверждения человеком.
- `src/leshy/browser_platform_runtime.py`: `chat()` и `chat_stream()` сохраняют совместимый fallback `owner_id="web:local"`; `src/leshy/owner_identity_runtime.py` также сохраняет такой fallback. Это не доказывает смешение данных: реальный Web bootstrap может подставлять уникальный owner. Необходимо проверить все HTTP/WS/Telegram точки входа.
- `BrowserPlatform._profile_arguments()` уже создаёт изолированный браузерный профиль по хешу непустого owner ID. Безопасность зависит от происхождения самого owner ID.
- `allowed_hosts` передаётся как аргумент действия. Нужно проверить, что конечная политика доменов определяется сервером, а не только моделью или пользовательским текстом.

## Требования к следующему совместимому исправлению

1. Сервер создаёт случайный криптографически стойкий идентификатор разрешения; хранит его хеш, owner UUID, session ID, тип операции, канонизированные аргументы и их digest, список доменов, время истечения, статус и аудит.
2. UI получает только непривилегированное описание ожидаемого действия. Подтверждение проверяется в авторизованном серверном маршруте с owner и session из доверенного контекста запроса; LLM и `action.arguments` не могут устанавливать `_approval_verified`.
3. Разрешение потребляется атомарно ровно один раз; повтор, истечение, отказ, смена owner/session, изменение аргументов или домена отклоняются до запуска браузера.
4. Для финансовых действий отображаются сумма, валюта, получатель и итоговый URL, если они известны; существенное изменение требует нового подтверждения.
5. Браузерный профиль и `allowed_hosts` вычисляются из серверной идентичности и политики. Проверять фактический URL после каждого перехода, включая redirect, а не полагаться только на текстовую инструкцию агенту.
6. Отсутствующий или недостоверный owner для изменяющих действий означает отказ (fail closed). Существующие чтения и непривязанные Telegram-чаты сохраняют работоспособность, но остаются изолированными.
7. Не менять существующие данные/профили и не объединять пользователей через `web:local`; миграции только добавочные и идемпотентные.

## Обязательные регрессионные сценарии

- Поддельный `_approval_verified=True` без серверного разрешения → отказ.
- Подтверждение владельца A используется владельцем B → отказ.
- Разрешение из сессии S1 используется в S2 → отказ.
- Изменение суммы, получателя, URL или параметров после подтверждения → отказ.
- Повторное использование, истёкшее или отклонённое разрешение → отказ.
- Параллельные запросы на одно разрешение → максимум одно выполнение.
- Редирект на запрещённый домен, локальный адрес или опасную схему → отказ.
- Два Web-клиента и два непривязанных Telegram user_id → разные owner, cookies и история.
- Подтверждённая Telegram/Web привязка → общий owner UUID без выдачи admin/OS-control.
- Проверка Web, Telegram и API end-to-end: ввод → запрос подтверждения → авторизованное решение → реальное действие → аудит.

# RDP: отдельное подтверждение передачи учётных данных CredSSP (1.10.171)

## Что реализовано

Модули `src/leshy/rdp_credssp_credentials.py`, `rdp_credssp_negotiator.py` и `rdp_credssp_channel.py` добавляют **внутренний, отключённый от Web/Telegram/LLM** этап передачи учётных данных после успешной проверки RDP-сервера. Никакой команды для отправки пароля из обычного чата нет.

1. Требуется ранее зарегистрированная привязка IP ↔ DNS/SPN ↔ SHA-256 **RDP TLS-сертификата**, независимая от SSH host key. Сначала устанавливается TLS 1.2+ и выполняется взаимно проверенный SPNEGO, затем GSS-зашифрованная проверка ключа сервера.
2. Только после `server_bound=True` отдельный доверенный вызывающий код должен передать объект `RDPCredentials` из **локального краткоживущего хранилища** и функцию `authorize_delegation(ip,dns)`. Она должна независимо подтвердить личность владельца, конкретный узел и его осознанное разрешение на передачу этих учётных данных.
3. `TSPasswordCreds` формируется как DER с UTF-16LE OCTET STRING для домена, имени пользователя и пароля. Его оборачивает `TSCredentials(credType=1)`. Только результат `GSS_Wrap` с обеспечением конфиденциальности помещается во **внутренний исходящий** `TSRequest.authInfo`; общий парсер по-прежнему **отклоняет входящие** `authInfo`.
4. Проверка полномочий выполняется до и после шифрования и перед передачей. Передача одноразовая на каждом канале; после ошибки соединение закрывается и **автоматического повтора нет**. Ошибка в `sendall` не позволяет утверждать, что данные не были доставлены.
5. Передаваемый пароль не попадает в ответы Web, JSON, логи, аудит или Knowledge. Тестовые секреты вымышленные. Буфер полученного DER очищается после использования, но Python не гарантирует очистку неизменяемых исходных строк и временных копий в системных библиотеках.

## Важное разграничение состояний

`credentials_delegated=True` означает только, что транспорт завершил отправку GSS-защищённого `authInfo`. Это **не доказывает**, что Windows приняла учётные данные или что доступен экран. `rdp_desktop_available=False` остаётся неизменным, а `autonomous_rdp_available` не включён.

На данном этапе **не реализованы** подтверждение ответа RDP-сервера на вход, MCS/GCC, графический канал, декодирование кадров, передача клавиш, мышь и интеграция в SuperAgent UI. Пользователю не предлагается вводить пароль в Web или Telegram. Прежний `.rdp` профиль системного клиента — отдельная возможность.

## Следующие этапы

1. Проверка результата NLA и межсистемная совместимость с реальным тестовым Windows RDP host: успешное завершение, неправильный пароль, смена/отзыв разрешения, перебои сети и точный признак отсутствия повтора.
2. Реализация MCS/GCC и лицензирования сеанса с ограниченными каналами, неизменяемой проверкой сертификата и корректным teardown.
3. Поддержка графического потока RGB/RGBA и наблюдения через существующий `RDPSessionController`, затем ввод с одноразовыми frame receipts.
4. Тестовый Windows/Linux E2E; только потом отдельный защищённый Web-контроллер и SuperAgent-управление экраном.

Без Docker, Guacamole, стороннего сервера или обязательного агента на целевом компьютере.

## Тестирование

`tests/test_rdp_credssp_credentials.py` содержит сценарии DER-кодирования, запрета входящего authInfo, отказа до server binding, отдельного подтверждения, невозможности повторной передачи и обработки отзыва прав. Тесты с имитациями транспорта не заменяют подключение к настоящему Windows. GitHub Actions остаются ручными.

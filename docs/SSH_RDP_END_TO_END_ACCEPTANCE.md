# SSH/RDP: обязательные критерии функциональной готовности (15.11.2026)

> Статус: **НЕ ГОТОВО / НЕ ПРОВЕРЕНО E2E**. Это контракт приёмки, не реализация и не разрешение на удалённые действия.
> База анализа: main `0c6302b66f0fade91ab7cfcca0c4593db8d96034`; `VERSION=1.10.152`.

## Обнаруженный разрыв

В `src/leshy/superagent_verified_ssh.py` прямо указано «read-only SSH OS inspection»; `_COMMANDS` содержит только `uname -s` и `cmd.exe /c ver`. Это **не** постоянный терминал и не выполнение пользовательского задания. Существующий механизм `_credential` читает JSON с паролем из файла: перед объявлением реализации соответствующей требованию «без хранения секретов» необходим отдельный аудит и переход на штатный агент/интерактивную авторизацию без сохранения пароля Лешим. Существующие PR #204, #207, #232, #234 требуют сверки с актуальным main и разрешённых проверок; нельзя сливать их только по наличию файлов.

## SSH — обязательный сквозной сценарий

1. В Web/Windows владелец открывает «Мои серверы», выбирает ранее криптографически сопряжённый узел и видит его проверенный host key, доступные права и состояние. Новые узлы и права по умолчанию запрещены.
2. Кнопка «Подключиться» создаёт реальную долгоживущую SSH-сессию с PTY (где поддерживается); доступны ввод, вывод, изменение размера, потоковая доставка, ограничение буфера, закрытие и корректное восстановление UI без повторного исполнения команды.
3. Леший определяет ОС, shell и capabilities на самом узле, выбирает команды с учётом среды; при неизвестной ОС не угадывает опасные команды.
4. Обычное текстовое задание преобразуется в план с видимыми командами и границами действия. До каждой операции проверяются серверная идентичность, принадлежность узла, capability и свежий approval с digest точного действия.
5. «Остановить» прерывает текущий процесс/сеанс, фиксирует неизвестный результат при обрыве и **не** повторяет потенциально побочное действие автоматически. Проверка результата — отдельный безопасный read-only шаг.
6. Секреты не попадают в persistent storage, историю, журналы, Knowledge, prompt или скриншоты; штатный SSH agent/OS credential UI предпочтительнее файлов с паролями.

## RDP — обязательный сквозной сценарий

1. Нативное подключение к разрешённому RDP-хосту с проверкой идентичности сервера, актуальной авторизацией и без стороннего шлюза/службы.
2. Действительно декодируемый видеопоток графического сеанса виден в Web/Windows, с управляемой частотой кадров и лимитом памяти; не считать успешный TLS/CredSSP handshake доказательством изображения.
3. Ввод мыши/клавиатуры передаётся в выбранный сеанс **только** при актуальном точечном разрешении и привязке к наблюдаемому кадру; устаревшие receipt и изменённый сеанс отклоняются.
4. Есть «Остановить», индикатор подключения, ошибки, явное отключение и очистка ephemeral-данных. Разрыв канала не приводит к автоматическому повтору опасного ввода.

## Негативные сценарии и критерий release

- Чужой owner, неподтверждённый peer, отозванный grant, неверный host key, повторный/устаревший approval: отказ **до** действия.
- Таймаут после отправки команды, усечённый stdout, разрыв PTY, повторная доставка Web-запроса: outcome=unknown, без автоповтора.
- Потеря RDP-кадра, изменение размеров/идентификатора сеанса, устаревший receipt, отключение пользователя: запрет ввода до нового наблюдения/подтверждения.
- Проверять Windows/Linux shell, Unicode/русский текст, несколько вкладок, мобильный Web, отмену и закрытие браузера; не допускать пересечения сессий пользователей.
- Перед merge: свежий main SHA, read-back изменённых файлов, Python syntax/static/API audit, разрешённые изолированные unit/regression и **реальный** SSH/RDP E2E. После merge: read-back main SHA, CI merged SHA, smoke старых Web/Telegram сценариев.
- При недоступности CI/раннера или запрете тестов статус остаётся **НЕ ПРОВЕРЕНО**; пользовательский релиз не объявляется готовым. К Kitesurf возвращаться только после подтверждения обоих маршрутов.

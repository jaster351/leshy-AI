# Global Swarm: автоматическое вступление новых узлов (этап 1, версия 1.10.92)

## Поведение при запуске

Новая установка Лешего имеет **«Автоматическое подключение к глобальному рою» = ВКЛ**.
Опция управляется в **Настройки → Распределённые вычисления**. Отключённое
значение сохраняется в LeshyBrain и не включается автоматически после обновления.

При наличии официального `LESHY_SWARM_BOOTSTRAP_URL` Леший без повторных
диалогов отправляет **подписанное** HTTPS-сообщение о присутствии.
При обрыве соединения повторяет регистрацию с ограниченным backoff.
Оператор bootstrap может увидеть сетевой IP посетителя и публичный
криптографический идентификатор узла. Это должно быть прямо указано
пользователю в описании установщика, лицензии и настройках.

**Внимание:** auto-join != добровольное предоставление GPU/CPU.
Этап 1 **никогда** не передаёт внешним участникам личные чаты, историю,
содержимое LeshyBrain, документы, файлы, приватные ключи, токены и пароли.
На этом этапе `resource_sharing_enabled=false` и
`remote_execution_enabled=false` независимо от числа участников.
Удалённые задачи не принимаются, общая память и глобальная репутация
не реализованы. Нельзя выдавать состояние `registered` за работающий
глобальный вычислительный пул.

## Настройка официального HTTPS bootstrap

Экземпляры должны знать хотя бы одну действующую точку входа. Нельзя
выдумывать домен: владелец проекта должен выделить реальный домен,
сертификат и работающий сервер. Затем в сборку/установщик включается
проверенный `LESHY_SWARM_BOOTSTRAP_URL=https://<ваш-реальный-домен>`.
Публичный код не должен содержать личных паролей или общих секретов.

Клиент обращается только к `POST /v1/swarm/hello`; не следует
перенаправлять запросы. Транспорт через HTTPS с обычной проверкой TLS,
без `verify=False`. Узел подписывает payload своим Ed25519-ключом
(`LeshyBrain/cluster/community-keys/`). Регистрационный payload содержит
только версию протокола, версию приложения и отключённые полномочия
исполнителя. IP присутствует на уровне сетевого соединения.

Для пилота сервер регистрации запускается на хосте с Python и установленным
пакетом Лешего, **только на loopback**:

```bash
python -m leshy.swarm_rendezvous --bind 127.0.0.1 --port 38865 --database ./swarm-rendezvous.sqlite3
```

Доступ с других устройств обеспечивается **настроенным администратором
HTTPS reverse proxy** на публичном домене с проксированием
`POST /v1/swarm/hello` к `http://127.0.0.1:38865`.
Перед публикацией включить TLS, проверку сертификатов, per-IP/per-key
rate limiting, ограничения соединений и длины тела, логи без приватных
payload, мониторинг и резервное копирование БД. Пилотная SQLite-система
регистрации **не** рассчитана на глобальную высоконагруженную эксплуатацию:
для неё необходим отдельный масштабируемый registry (Redis/Postgres,
высокая доступность, защита от Sybil/DoS, несколько bootstrap-узлов).

### Локальный тест без интернета

В **тестовом** окружении допустим один компьютер как сервер и клиент:

```powershell
$env:LESHY_SWARM_DEV_ALLOW_HTTP="1"
$env:LESHY_SWARM_BOOTSTRAP_URL="http://127.0.0.1:38865"
```

На другом компьютере `127.0.0.1` обозначает **самого себя**, поэтому
такой адрес не подходит для испытания нескольких устройств. Не включайте
`LESHY_SWARM_DEV_ALLOW_HTTP` в публичные сборки.

## Статус и выключение

```powershell
Invoke-RestMethod "http://127.0.0.1:8765/v1/swarm/status" | ConvertTo-Json -Depth 5
```

В интерфейсе есть переключатель для автоучастия. Если bootstrap не задан,
`state=waiting_for_bootstrap` и `bootstrap_configured=false`.
При рабочем соединении `state=registered` — **только регистрация**.
`global_mesh_connected=false` до появления подтверждённого P2P-транспорта.

## Что требуется перед реальным распределением вычислений

1. Отдельное добровольное разрешение на передачу задач чужих пользователей,
   настройка лимитов CPU/GPU/RAM/сети/батареи и мгновенное выключение.
2. Authenticated end-to-end transport, проверка узлов, NAT traversal
   через libp2p relay/hole-punching, защита от Sybil/DoS и репутация.
3. Подписанные контракты вычислений с ограниченными capabilities,
   песочницей/изоляцией, отменой, таймаутами, quotas и недоверием к
   удалённым результатам.
4. Единый Web Gateway с OIDC/passkeys, изоляцией tenant/owner и
   контролем того, какие данные разрешено отправить чужим узлам.
5. Журнал и сверка подписанных **общедоступных подтверждённых** знаний
   (без пользовательских переписок и приватной памяти), версии и
   хеши набора фактов, антиэнтропийная синхронизация и аудит.
6. Планировщик запросов, параллельные подзадачи и арбитр, дающий
   **один ответ**; отдельно — строгая аренда для одного Telegram poller.
7. Полномасштабные тесты нагрузок, отказов, NAT, эмуляции вредоносных
   участников и проверки безопасности до публичного включения worker.

Подготовленная регистрация позволяет масштабировать обнаружение по
реальному публичному bootstrap, когда он будет развёрнут.
Она пока **не ускоряет** генерацию и не заменяет LAN-синхронизацию.

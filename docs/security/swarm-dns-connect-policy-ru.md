# Безопасное подключение к публичным узлам: DNS и HTTPS

Статический аудит 09.11.2026, исходный `main`: `2133b41967571af4adf0c2a7ec2e411c1bd5ad9b`. Документ описывает **незавершённое** требование безопасности; наличие проверки URL не доказывает безопасность фактического соединения.

## Наблюдаемый маршрут

`SwarmMembership._hello()` в `src/leshy/swarm_membership.py` вызывает `urllib.request.build_opener(ProxyHandler(), _RejectRedirect()).open(req)`. `bootstrap_endpoint()` не проверяет разрешённые IP. `_seed_url()` в `swarm_bootstrap.py` отсекает частные **буквальные** IP, но не результат DNS. При системном прокси DNS может разрешаться прокси-сервером, и локальная проверка DNS не гарантирует фактический адрес назначения.

## Требуемая политика

1. Публичный bootstrap: HTTPS, допустимый DNS-адрес, отсутствие userinfo, query, fragment, запрещённых локальных суффиксов и нестандартных URL-форм; строго запрещены редиректы.
2. Без прокси: получить все A/AAAA адреса и отвергнуть весь набор при наличии хотя бы одного непубличного IP. Соединяться только с выбранным проверенным IP, сохраняя исходный hostname для TLS SNI и проверки сертификата; повторное DNS-разрешение между проверкой и подключением недопустимо. При смене адреса повторить полную проверку.
3. С HTTPS-прокси: локальное DNS-разрешение не обеспечивает защиту от rebinding на стороне прокси. Для недоверенных публичных узлов применять fail-closed, если нельзя гарантировать проверку адреса на фактическом egress. Не отключать системный прокси молча и не обходить корпоративную сетевую политику.
4. HTTP разрешён исключительно для явного локального пилота и loopback. Локальный пилот не должен автоматически расширять разрешения публичного роя.
5. Ошибки DNS/TLS/прокси должны иметь ограниченный timeout и безопасную диагностику без публикации идентификаторов, токенов, адресов из пользовательской конфигурации или приватных данных. Сохранять существующие статусы UI и контракт регистрации.
6. Не считать bootstrap-узел доверенным для исполнения задач или доступа к пользовательской памяти даже после успешной регистрации.

## Обязательные regression/eval сценарии (пока не запускались)

- Публичный DNS -> 127.0.0.1, RFC1918, link-local, IPv6 ULA, IPv4-mapped IPv6; смешанный набор публичных/приватных адресов.
- DNS rebinding между предварительной проверкой и socket connect; удостовериться, что фактическое соединение идёт только к ранее проверенному IP.
- Прокси с удалённым DNS, PAC и системным HTTPS_PROXY: запрет обхода egress-политики и fail-closed, если невозможно проверить destination.
- TLS: SNI и hostname verification сохраняются при pinning IP; ошибочный сертификат отклоняется.
- HTTP 301/302/307/308 не приводят к следующему соединению.
- Локальный HTTP-пилот работает только при явном разрешении; публичный HTTPS остаётся обязательным.
- Недоступность DNS, timeout, ошибки прокси и большой ответ не блокируют пользовательский чат.
- Негативный результат не меняет identity, историю, память, настройки и список разрешений.

## Критерий готовности

После реализации необходим read-back из `main`, подтверждение реального маршрута `_hello -> transport -> socket`, просмотр автоматически выполненного CI и отдельная проверка пользовательского runtime. До этого Issue #132 остаётся открытой. Локальные сборки и автотесты без разрешения владельца не запускать.

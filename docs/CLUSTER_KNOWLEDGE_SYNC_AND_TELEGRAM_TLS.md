# Синхронизация знаний между доверенными ПК и диагностика Telegram TLS

## Почему ПК №2 не подключается к Telegram

В журналах с 07.11.2026 присутствуют две разные группы ошибок:

- `CERTIFICATE_VERIFY_FAILED: self-signed certificate in certificate chain`;
- `Прокси Telegram недоступен (URLError)`.

Такие же ошибки сертификата возникали при скачивании модели.
Это указывает на сеть/прокси/доверенные корневые сертификаты на ПК №2,
а не на Git, RTX 3070 или рабочий токен бота.

Выполните **без прав администратора**:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\windows\Test-LeshyTLS.ps1
```

Сценарий проверяет `https://api.telegram.org` и `https://huggingface.co`
в Windows и системном Python **без секретного токена**. Он не меняет
реестр, прокси, хранилище сертификатов и настройки шифрования.

Если Windows подтверждает HTTPS, а Python отвергает сертификат,
проверьте окружение Python и сертификаты доверенного
прокси/антивируса. Если ошибка присутствует и в Windows, проверьте
системный прокси, защитное ПО и доверенный корневой сертификат.

Когда Ваш администратор сети подтвердил конкретный корневой CA и
передал его в PEM-формате, перед запуском Лешего можно указать:

```powershell
$env:LESHY_TELEGRAM_CA_BUNDLE = 'C:\certificates\trusted-proxy-root.pem'
.\dist\Leshy\Leshy.exe
```

CA добавляется к штатным доверенным сертификатам; имя сервера
`api.telegram.org` и цепочка сертификатов **по-прежнему проверяются**.
При недоступном/невалидном PEM Леший покажет ошибку, но не отключит TLS.
Запрещено использовать `verify=False`, `CERT_NONE` или
`check_hostname=False` для восстановления соединения.

Если прокси Telegram включён в интерфейсе, проверьте отдельно
его схему (HTTP/SOCKS5), адрес, порт и доступность. Когда прокси не
требуется, выключите только **Telegram-прокси** в настройках,
а не всю проверку сертификатов.

**Важно о Telegram:** один и тот же bot token нельзя надёжно использовать
одновременно в двух независимых потребителях `getUpdates`.
При успешном TLS это может привести к HTTP 409 Conflict.
До появления распределённой аренды Telegram polling оставьте одного
активного Telegram-получателя; остальные компьютеры участвуют в
вычислениях и синхронизации знаний.

## Автоматическая репликация общих знаний

После однократного доверенного сопряжения ПК (одинаковый
`cluster-secret`, разные `node-id`) каждый узел через UDP 38765
обнаруживает других и **каждые 5 секунд** получает от них новые записи
общих знаний (передача производится через TCP 8765).

Обмен подписан HMAC-SHA256 поверх существующей кластерной идентичности.
Сами данные зашифрованы отдельным ключом Fernet, производным от
кластерного секрета. Открытый HTTP не переносит содержимое знаний
без шифрования. Внешние HTTP-перенаправления и системный прокси
для LAN-синхронизации запрещены.

Передаются: краткие утверждения, тема, публичный исходный URL,
тип данных (статические или динамические), время последней проверки.
На принимающем узле записи всегда становятся `candidate`, даже если
отправитель уже пометил их как `trusted`. Последующая независимая
верификация необходима для продвижения доверия.

Никогда не пересылаются в этом канале: Telegram bot token,
прокси-пароли, личные сообщения, чат-сессии, память конкретного
владельца, ключи API, cookies, модель GGUF и другие файлы `LeshyBrain`.
Для персональных данных в будущем понадобится отдельная настройка
синхронизации, согласие владельца и контроль конфликтов.

Репликация не запускает самообучение в интернете. Она переносит
уже накопленные публичные знания даже когда автономное обучение
выключено. Когда кластер отключён или не завершено доверенное
сопряжение, репликация ничего не передаёт.

**Граница между знаниями и персональной информацией.** Проверка источника дополняется эвристическим фильтром очевидных контактных данных и секретов в тексте отправляемой и получаемой записи. Это не полноценная анонимизация: публичная страница может содержать личную информацию, не распознаваемую фильтром. См. [единый архитектурный контракт](SWARM_DATA_BOUNDARIES.md).

## Контроль в консоли и API

Консоль показывает каждые 30 секунд или при изменении:

- состояние Telegram: настроен, TLS-сертификат, прокси, API;
- число узлов, очередь и задачи;
- состояние синхронизации, количество полученных и отданных записей,
  время последнего удачного обмена.

Детальная диагностика:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/v1/cluster/knowledge-sync/status | Format-List
```

В настройках кластера эти же показатели обновляются при открытой панели
каждые 15 секунд.

Важное ограничение: обмен является **почти реальным временем**
(опрос раз в 5 секунд), а не транзакционной репликацией SQLite.
При недоступности соседа синхронизация возобновится автоматически,
но перенос большого объёма знаний может занимать несколько циклов.

## Проверки после сборки 1.10.83

1. На ПК №2 проверить TLS без Telegram-токена.
2. После настройки сертификата проверить `getMe` через сам Леший.
3. Убедиться, что оба ПК видят `peer_count: 2`.
4. Добавить на ПК №1 тестовую запись из публичного источника,
   убедиться в её появлении на ПК №2 как `candidate`.
5. Отключить один узел, добавить вторую запись и снова включить:
   после reconnect запись должна попасть на второй ПК без ручного копирования.
6. Проверить, что сессии, память пользователей, секреты и `GGUF`
   не были перенесены.

Реальные проверки на двух ПК пользователь проводит после пересборки.
Документация сама по себе не доказывает успешное соединение.

## Найденная проблема безопасности

На момент сверки в `main` повторный запрос снимка мог оставить
**действующим старое разрешение на клик**, если новое наблюдение было отклонено
при проверке владельца, не удалось из-за обрыва, либо завершилось ошибкой
формата. Сжатые/необработанные `opaque` кадры могли получить действие как
обычные декодированные RGB кадры. Блокировка должна действовать *до*
повторного получения кадра, но только для того же владельца, а новый receipt
должен публиковаться лишь после полной проверки байтов, digest и времени.

В отдельной ветке `fix/rdp-atomic-decoded-receipts-20261121` объединены
эти исправления из существующих черновых наработок и отдельные регрессии.
Наличие ветки **не означает**, что Windows RDP backend работает.

## Дальнейший порядок работ (параллельные независимые направления)

**Безопасность:** выполнить все receipt-тесты, проверить отзыв прав в каждом
сетевом шаге, исключить повтор опасного действия при обрыве, проверить
подлинность owner/node вне запросов модели.

**Протокол:** протоколировать только безопасные стадии (без паролей и токенов),
сверить настоящий Windows TLS/SSPI/NLA/MCS/Client Info, затем добавить
лицензирование, Demand Active/Confirm Active, finalization и bitmap/capabilities.

**Графика/UI:** реальный backend в Windows/Linux, декодирование кадра,
проверенный рендеринг в существующем UI, координаты/DPI/resize; только потом
подключать разрешённые мышь и клавиатуру.

**Тестирование:** повторяемые Windows/Linux unit + loopback + настоящий
изолированный Windows RDP E2E с успешными и отказными сценариями. Текущие
GitHub workflow для RDP запускаются вручную (`workflow_dispatch`), а не
автоматически; результат не появится от одного коммита.

Независимые операции чтения/анализа можно распараллеливать ограниченным
пулом; изменяющие операции над `main` и установка версий должны выполняться
последовательно во избежание потери чужих коммитов. Запрос 10²¹ потоков
физически невыполним и не обеспечивает ускорения.

## Критерий закрытия RDP

В `main` должен быть проверенный путь: authenticated owner -> trusted node
-> pinned TLS/NLA -> лицензирование/активация -> видимое и декодированное
изображение -> подтверждённый ввод -> безопасный Stop/отзыв/закрытие.
Не считать RDP завершённым до реального E2E на Windows и подтверждения
работоспособности с сохранением SSH, Web и Telegram.

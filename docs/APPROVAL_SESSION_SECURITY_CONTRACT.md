# Контракт безопасного подтверждения внешних действий (проект)

Статус: **проект решения, не реализовано**. Документ не означает готовности Web/Telegram/API.

## Угроза

Текущий `ApprovalBroker` связывает одноразовый `approval_id` с `owner_id`, но не с `session_id`. При совпадающем владельце подтверждение может быть использовано в другой сессии. Дополнительно нужно исключить возможность выполнять действие по клиентскому `approved=True` без серверной проверки.

## Серверный контракт

1. При создании запроса сервер определяет `owner_id` из проверенной аутентификации, `session_id` — из принадлежащего этому владельцу диалога. Не принимать произвольный `owner_id` из тела запроса как доказательство личности.
2. `PendingApproval` хранит обязательные `owner_id`, `session_id`, `approval_id`, `expires_at`, неизменяемый снимок действия и SHA-256 канонически сериализованных параметров. Срок действия короткий; после перезапуска неподтверждённые разрешения исчезают.
3. Запросы просмотра, отклонения и исполнения проверяют **оба** идентификатора. Несовпадение возвращает одинаковую безопасную ошибку «не найдено», без раскрытия существования чужого разрешения.
4. Исполнение атомарно извлекает одноразовое разрешение под блокировкой; повторное использование, просрочка, отказ, изменение параметров и действие с другим отпечатком запрещены.
5. `approved=True` из Web/Telegram/API не даёт разрешения само по себе. Только успешный серверный `consume(owner_id, session_id, approval_id)` позволяет исполнение сохранённого снимка.
6. Разрешение на конкретное действие не означает разрешения на другой URL, сумму, получателя, инструмент или изменение профиля. Для каждого нового действия требуется отдельный запрос.
7. Связка Telegram ↔ Web меняет общий owner только после одноразового подтверждения привязки. Непривязанные Telegram user_id изолированы; обычная привязка не даёт административных прав.
8. Логировать безопасные `approval_id`, `owner_id` (или его безопасный псевдоним), `session_id`, отпечаток, решение и причину отказа без секретов, cookies и платёжных реквизитов.

## Порядок совместимого внедрения

- Прочитать актуальный `main`, создать ветку от точного SHA; проверить все вызовы `request/list/deny/consume` и `resolve_approval`.
- Ввести серверное связывание сессии в брокер и runtime; не заменять отсутствующую сессию общим fallback.
- Обновить Web/Windows/API/Telegram маршруты одновременно, с явным отказом для неавторизованного контекста; сохранить обычный Telegram-чат без Web-авторизации.
- Проверить, что UI показывает именно тот снимок действия, который будет исполнен. Привязать отображение подтверждения к нужной сессии.
- После каждого изменения выполнить read-back. Локальные сборки и тесты не запускать без разрешения; наблюдать существующий внешний CI.

## Обязательные регрессии (ещё не реализованы)

| Сценарий | Ожидаемый результат |
|---|---|
| Верный владелец и верная сессия | Одно разрешённое исполнение |
| Верный владелец, другая сессия | Отказ без расходования чужого разрешения |
| Другой владелец, та же строка сессии | Отказ |
| Пустой owner или session | Отказ |
| Повторный consume | Отказ |
| Просроченное / отклонённое разрешение | Отказ |
| Изменение вложенных аргументов, URL, суммы | Выполняется только первоначальный снимок либо отказ |
| Клиент прислал `approved=True` без approval_id | Отказ |
| Конкурентные consume | Не более одного успешного |
| Telegram непривязанного пользователя | Изоляция owner/session |
| Telegram reply на старое сообщение | Сохраняется приоритет выбранного сообщения |
| Restart процесса | Старые разрешения недействительны |

**Критерий готовности:** end-to-end трасса пользовательского запроса через Web/Telegram/API до реального исполнения, отрицательные сценарии и read-back кода в `main`. Наличие этого документа, классов или переключателей готовностью не считается.

## Уточнения по статическому аудиту 5 ноября 2026

- На момент аудита в `src/leshy/action_approvals.py` методы `request(owner_id, action)`, `list(owner_id)`, `deny(owner_id, approval_id)`, `consume(owner_id, approval_id)` не принимают сессию. Нельзя считать защиту реализованной, пока все четыре метода и их вызывающие маршруты не проверяют серверно установленную сессию.
- Проверка должна использовать не просто переданный клиентом `session_id`, а доказанную сервером принадлежность сессии аутентифицированному владельцу. Для Telegram изолировать идентификаторы с учётом `user_id` и чата; привязку к Web-owner подтверждать отдельно.
- Канонический отпечаток действия должен охватывать тип инструмента, URL/домен, метод, получателя, сумму/валюту и все вложенные аргументы, влияющие на эффект. Сериализация должна быть детерминированной; неподдерживаемые/несериализуемые значения следует отклонять, а не пропускать из хеша.
- Одноразовость гарантируется атомарным извлечением под блокировкой до начала исполнения. При ошибке исполнения нельзя незаметно повторно использовать тот же токен; новая попытка требует нового разрешения. UI обязан показывать тот же неизменяемый снимок, что исполняется.
- Запрещён обратный совместимый fallback к `web:local` или пустой сессии для опасных действий. Временно несовместимые маршруты должны безопасно отказывать, не блокируя обычный чат и READ-операции.
- Для каждого write требуется свежий SHA файла, а после изменений — read-back и проверка всех точек вызова. До прохождения внешнего CI и E2E статус остаётся «не реализовано».

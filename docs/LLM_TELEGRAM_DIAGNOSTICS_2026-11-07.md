# Исправления по логам 7 ноября 2026: LLM и Telegram

Подтверждено логами Windows 1.10.37: после перезапуска без новых сообщений
список старых сессий запускал фоновую LLM-генерацию заголовка. Vulkan
потратил около 83 секунд и вернул пустое содержимое с
`finish_reason=length`, после чего начинался fallback OpenVINO.
`learning_enabled=false` при этом читалось корректно; указанная
фонова задача не является доказательством включённого самообучения.

Изменения:

- 1.10.54: обычное открытие истории больше не запускает auto-title LLM.
- 1.10.55: Telegram-фотографии идут в отдельный vision маршрут, а не
  text-only модель; сохраняются разрешённые Telegram ID и Reply.
- 1.10.56: более консервативная оценка Unicode-контекста на 4096
  и отказ от каскада долгих GPU/NPU/CPU retry.
- 1.10.57: ожидание одиночного llama-server запроса по умолчанию
  Vulkan 70 с, OpenVINO 45 с, CPU-server 90 с.
  Для длительных рассуждений можно задать
  `LESHY_LLM_REQUEST_TIMEOUT_SECONDS=120` (диапазон 20–180 с).
  Это HTTP timeout, не жёсткая гарантия времени ответа.

## Локальная vision-модель

Леший не может описывать фотографию, если подключена только текстовая
модель. Нужен локальный OpenAI-совместимый vision endpoint
с фактической поддержкой изображения. Пример переменных Windows:

```powershell
$env:LESHY_VISION_ENDPOINT = "http://127.0.0.1:8080/v1/chat/completions"
$env:LESHY_VISION_MODEL = "ИМЯ_УСТАНОВЛЕННОЙ_VISION_МОДЕЛИ"
```

Эти команды только устанавливают адрес и имя, но не скачивают модель.
Укажите реальный порт и имя уже запущенной локальной vision-модели;
внешние endpoints запрещены. Изображение не записывается в журнал и базу.

## Проверка после локальной сборки

Открыть историю после простого перезапуска: без вызова LLM авто-title.
Проверить длинный русский запрос и Telegram Reply: без HTTP 400 context.
Проверить отказ Vulkan: без последовательных многоминутных retries.
Отправить фото без подписи и с вопросом в Telegram: корректная
диагностика без vision или описание при подключённой vision.
Тесты и GitHub Actions не запускались по просьбе владельца.

## Дополнительная диагностика потокового режима (1.10.58–1.10.59)

В полном логе обнаружено 404 события `adaptive_llm_circuit_open`
(преимущественно фоновые заголовки), а также потоковый
`adaptive_llm_stream_backend_ok` с задержкой около 610 секунд.
Причина длительности подтверждена в исходниках:
`_MAX_AUTO_CONTINUATIONS = 6` допускал до семи последовательных
раундов ответа и потоковый fallback был независим от исправлений
обычного `AdaptiveLLM.chat`.

Исправлено: максимум одно продолжение, отсутствие продолжения
пустого ответа, ограничение продолжения после долгого первого раунда,
применение бюджета контекста к потоковым запросам **до** llama-server
и отказ от медленного каскада fallback между аппаратными backend.

Ограничение: HTTP/SSE может блокироваться на ожидании отдельных байтов
до сокетного timeout; это не гарантия жёсткого wall-clock лимита. Нельзя
считать исправление полностью проверенным, пока владелец не установит
обновлённую версию и не воспроизведёт сценарии на Windows.

## Telegram Reply на фотографию (1.10.60)

Если пользователь отправил фото, а следующим сообщением сделал Telegram
Reply на фото и написал вопрос, берём image attachment из
`reply_to_message`, а вопрос — из текущего текстового сообщения.
Ответ возвращается Reply на текущий вопрос. Сохраняются прежние
allow-list пользователя, адресация группы и owner ID; текстовый
LLM-маршрут в этом случае не вызывается.

Отдельные сообщения об ошибках vision backend различают HTTP 400/422
(неподходящий мультимодальный запрос), HTTP 404 (endpoint/модель
не найдены), недоступный сервер/таймаут и отсутствие настроенной модели.
Секрет Telegram bot token не попадает в логи исключений.

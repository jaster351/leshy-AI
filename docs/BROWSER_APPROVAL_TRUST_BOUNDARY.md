# Граница доверия Browser Agent: требования и проверки

Статус: **план безопасности, не реализация**. Актуальная отправная точка для аудита — `main` на коммите `9203a83fe46ca5c9ac60bd08f09f6144a18937f6` (2026-11-06). Ни один пункт ниже нельзя объявлять исправленным без проверки пользовательского маршрута.

## Зачем это нужно

Леший может выполнять действия в браузере. Чтение страницы и отправка формы с оплатой имеют разный риск. Слова модели, параметр `_approval_verified` и визуальная кнопка сами по себе не доказывают, что действие подтвердил именно владелец соответствующей сессии.

## Требуемое поведение

1. Для каждого изменяющего или необратимого действия сервер создаёт случайное одноразовое разрешение, привязанное к проверенным `owner UUID`, `session ID`, типу действия, каноническим аргументам и сроку действия.
2. Подтверждение поступает только через авторизованный серверный маршрут. Модель, HTML страницы и аргументы инструмента не могут устанавливать статус подтверждения.
3. Потребление разрешения атомарно: два параллельных запроса не должны дважды выполнять действие. Повтор, истечение, отмена, смена владельца/сессии или аргументов означают отказ.
4. Перед подтверждением показываются назначение действия, домен, а для платежа — сумма, валюта и получатель. Изменение этих данных требует нового подтверждения.
5. Разрешённые домены задаёт серверная политика. После переходов и перенаправлений проверяется фактический URL; локальные адреса и опасные схемы блокируются по политике.
6. Отсутствующий проверенный владелец означает отказ для привилегированного действия. Непривязанные пользователи Telegram продолжают обычный чат с отдельными owner и памятью; привязка Telegram/Web не даёт административных прав.
7. Изменения хранилища должны быть добавочными и идемпотентными; запрещено объединять профили через общий `web:local`.

## Регрессионные сценарии для будущих тестов

- Поддельный `_approval_verified=True` без серверного разрешения → отказ.
- Разрешение владельца A или сессии S1 используется владельцем B или сессией S2 → отказ.
- Подмена суммы, получателя, домена или аргументов после подтверждения → отказ.
- Повторное, просроченное и отменённое разрешение → отказ.
- Два одновременных подтверждения → не более одного исполнения.
- Redirect на запрещённый домен, loopback или опасную схему → отказ.
- Два Web-профиля и два непривязанных Telegram user_id → независимые данные и браузерные профили.
- Подтверждённая привязка Telegram/Web → общий owner UUID без автоматических прав OS-control.
- End-to-end Web/Telegram/API: запрос → показ подтверждения → авторизованное решение → исполнение → аудит.

## Проверка готовности

Только после статической проверки всех точек вызова, проверки сигнатур и негативных маршрутов, read-back кода в `main` и подтверждённых end-to-end проверок можно переносить сценарии из раздела «требуемое поведение» в «исправлено». Локальные сборки и тесты без отдельного разрешения пользователя не запускать. Ошибки внешнего CI не маскировать.

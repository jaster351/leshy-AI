# RDP: единый TLS-канал для CredSSP без передачи пароля

Новый модуль: `src/leshy/rdp_credssp_channel.py`.

## Реализовано

Это следующий шаг от отдельной проверки TLS к **живому соединению**:
сохраняется то же самое TCP/TLS-соединение после X.224, на котором может
выполняться последовательный CredSSP/TSRequest обмен.

- Серверно подтверждённая авторизация владельца и соответствия зарегистрированных
  IP-адреса и DNS-имени Kerberos-службы (`TERMSRV/<dns>`) обязательна
  до сетевого подключения и перед каждым защищённым сообщением.
- Только буквальный IP-адрес (не произвольный URL или имя из запроса модели)
  для TCP; допустимое отдельное DNS-имя передаётся только при независимом
  подтверждении его привязки к указанному узлу.
- X.224 должен выбрать **CredSSP** или **CredSSP-EX**. Отказ от TLS-only
  и legacy Standard RDP Security в этом модуле.
- TLS версии 1.2+; точное сравнение SHA-256 DER-сертификата с отдельно
  зарегистрированным отпечатком **до создания GSS/SPNEGO контекста**.
  SSH host-key hash не используется как подмена RDP TLS pin.
- `read_tsrequest` читает ровно одно полное ASN.1 DER-сообщение даже при
  частичных TCP/TLS чтениях; допускает только каноническое кодирование
  длины, ограничивает объём 256 КиБ и отклоняет запрещённый `authInfo`.
- Один общий монотонный дедлайн для TCP/X.224/TLS/CredSSP; при смене прав,
  несоответствии сертификата, ошибке DER или SPNEGO канал уничтожается.
- `authenticate_server()` использует системный SPNEGO из PR #231 и
  `CredSSPClient` для проверки зашифрованного TLS public-key binding
  без делегирования пароля. Соединение остаётся живым внутри
  `with PinnedRDPCredSSPChannel(...) as ...` и закрывается при выходе.

Результат `RDPBindingStatus` различает флаги `server_bound=True` и
`credentials_delegated=False`, `rdp_desktop_available=False`. Даже при
успешном подтверждении ключа сервера **это ещё не вход в Windows**.

## Ограничения

Это внутренний API без маршрута HTTP, Telegram или инструментального вызова
из языковой модели. Публичный пользовательский вызов без интеграции с
`RemotePermissionPolicy`, независимым регистрационным хранилищем RDP TLS pin
и проверенным соответствием IP/DNS/SPN запрещён.

Прежний `rdp_tls_probe.py` оставлен для короткой диагностической проверки,
он не заменён и продолжает закрывать соединение после TLS. Новый внутренний этап может отправить зашифрованные TSCredentials **только**
после отдельного подтверждения владельца и проверки привязки сервера.
Он ещё не доказывает вход в Windows, не создаёт MCS/каналы, не декодирует
графику и не управляет мышью/клавиатурой. `autonomous_rdp_available`
остаётся `False`.

На Linux для полного SPNEGO нужны системный GSSAPI и действующий Kerberos-билет;
на Windows используется SSPI текущей авторизованной сессии. При отсутствии
подходящих учётных данных поведение — отказ, а не отключение защиты.

## Проверки

Добавлены тесты с фрагментированными TLS-ответами, двухэтапным обменом
TSRequest, проверкой сертификата, неподдерживаемого TLS-only, отказом владельца,
пределами размера, изменением разрешений и запретом `authInfo`. В текущем
изолированном окружении реальный Windows RDP host недоступен; полный E2E
не проверен.

Нормативный источник: <https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cssp/385a7489-d46b-464c-b224-f7340e308a5c>.

Следующий этап — на реальном Windows RDP-сервере подтвердить результат NLA,
проверить запрет повторной передачи секретов, затем реализовать MCS/каналы,
графику и управление вводом.

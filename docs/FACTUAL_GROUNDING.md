# Проверяемые факты и устранение галлюцинаций Лешего

## Проблема

На вопрос об авторах GitHub Issues Леший сообщал имена и число записей,
хотя проверенного результата GitHub API в контексте не было. Для локальной
LLM фраза «проверил GitHub» без свидетельства вызова — обычная
генерация текста, а не доказательство действия.

**Цель:** снижать число неподтверждённых утверждений без запрета на
самообучение, эксперименты, веб-поиск или создание новых инструментов.

## Реализованный первый уровень, версия 1.10.114

1. Для запросов об авторах, комментариях и количестве Issues/PR
   канонического `jaster351/leshy-AI` вызывается
   `GitHubRepositoryEvidence`. Имена и количество получаются только из
   GitHub REST API; модель не придумывает список.
2. `GET /issues?state=all` возвращает и Issues, и PR.
   Адаптер **обязательно** отделяет PR по полю `pull_request`, затем
   читает `/issues/comments` и `/pulls/comments`.
   В случае неполной пагинации, ошибочного JSON, недоступности сети или
   API rate limit выдаётся ответ «не удалось подтвердить», а не догадка.
3. Каждый успешный/неуспешный вызов отмечается
   `VerifiedToolReceipts` с типом инструмента, временем и digest результата.
   Receipt — свидетельство вызова, **не** гарантия истинности содержания.
4. Переиспользование полного снимка до 15 минут сокращает нагрузку
   на GitHub API. В ответе всегда указывается реальное время получения
   данных и то, когда использован кэш.
5. Проверка подключена и к `LeshyApp.chat()`, и к потоковому
   `RealtimeChatManager.stream()`, включая короткие уточнения
   «А что написал не ты?» после явного вопроса о репозитории.
6. Во всех обычных генерациях добавлено короткое правило
   `FACTUAL_EVIDENCE_POLICY`: не заявлять об использовании инструмента,
   если в контексте нет его результата; менять факт на неопределённость
   при невозможности проверки.
7. Новый инструмент отражён в `capabilities.json`, а runtime-статус
   проверяется **без сетевого вызова** по свежему завершённому снимку.

## Важные ограничения

- Этот модуль проверяет **только указанный репозиторий**.
  Произвольные другие GitHub-репозитории пока идут обычным маршрутом и
  не получают гарантий типизированной сверки.
- GitHub API перечисляет аккаунты, а не авторов текста среди людей/AI.
- Учёт отдельных PR review submissions, GitHub Discussions и комментариев
  к коммитам в этом инструменте не реализован: не утверждать, что они
  проверены.
- Общая инструкция модели уменьшает риск, но не может гарантировать
  отсутствие ошибок в иных темах. Для этого нужны структурированные
  адаптеры других провайдеров, проверка полноты, журнал происхождения и
  регрессионные тесты на реальных ошибках из runtime-логов.
- API использует публичный HTTPS без токенов GitHub и не передаёт
  пользовательские данные. Не требуется доступ к приватным репозиториям.
- Никакие разрешения управления ОС не расширяются и самостоятельное
  обучение Лешего не выключается.

## Следующий этап

Обобщить схему `EvidenceResult {source, fetched_at, complete, errors,
receipt_id, facts}` для запросов о GitHub, веб-страницах, поиске,
состояниях узлов и документах. Вести набор эталонных вопросов/ответов,
включая инцидент с «46 вопросами и 10 авторами», чтобы каждое обновление
могло проверять не только красоту текста, но и его достоверность.

В этом изменении исходники проверены статически. Локальные Windows-сборки,
автотесты и реальная работа GitHub API на ПК1/ПК2 пока не проверены.

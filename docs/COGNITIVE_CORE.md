# Leshy Cognitive Core — этап 1 (1.10.38)

## Зачем это нужно

Фоновый SuperAgent до этого мог пометить внешнюю задачу как «готово» по
одному текстовому ответу LLM. Но генерация текста сама по себе не устанавливает
программу, не коммитит код и не отправляет сообщение.

В первом этапе добавлен детерминированный контроль завершения задач:

- Запросы на явные внешние операции не получают статус `ready` без
  квитанции от реального исполнителя.
- Обычные текстовые задачи (объяснить, составить обзор, написать инструкцию)
  продолжают работать без новых ограничений.
- При отсутствии исполнения задача остаётся `blocked`, а не выдаёт
  ложное сообщение об успехе.
- Схема SQLite, пользовательская память и LeshyBrain не изменяются.

## Ограничения

Это **не** полноценный Cognitive Core: планирование, верификатор результата,
восстановление шагов и автономный инструментальный исполнитель будут
подключаться поэтапно. В текущем SuperAgent нет полноценного набора
изменяющих инструментов. Поэтому реальные задачи установки, публикации или
изменения файлов корректно блокируются до реализации безопасного исполнителя.

Квитанция подтверждает лишь факт успешного вызова изменяющей операции, а не
правильность её эффекта. Для завершения таких задач позже потребуется
проверять ожидаемое состояние и делать откат при ошибке.

## Как проверить локально

Сборка и автотесты в GitHub не запускаются. Владелец может проверить код
локально, в том числе через `python -m unittest tests.test_cognitive_core -v`.
Проверьте команду `/agent установи программу`: задача не должна получать
статус «готово» без реально выполненной установки.

## Этап 2 (1.10.39): ограниченные инструменты чтения

SuperAgent теперь может в пределах одной задачи запросить не более **двух**
чтений через строгий allow-list:

- `knowledge.search` — до пяти записей из доверенных знаний; метаданные БД
  и дополнительные поля не передаются в LLM;
- `runtime.version` — текущий номер версии из канонического файла.

Инструментальные ответы из полной JSON-команды модели разбираются
детерминированно, а квитанции создаются существующим
`VerifiedToolReceipts` **после фактического выполнения** инструмента.
Неподдерживаемые, повторяющиеся или ошибочные вызовы завершают задачу
статусом `blocked`. Разрешений на ОС, shell, запись файлов, покупку или
MCP-mutate этот этап **не выдаёт**. Квитанции чтения не подтверждают
изменения системы и не переводят внешние задачи в `ready`.

Веб-поиск SuperAgent остался прежним отдельным маршрутом; новые чтения
не запускают интернет, не управляют переключателем самообучения и не
изменяют пользовательские данные. Схема SQLite не менялась.

Для локальной проверки можно запустить
`python -m unittest tests.test_cognitive_tools -v`; в GitHub
сборка и тесты не запускались.

## Этап 3 (1.10.42): журнал шагов и восстановление

Для каждого фактического чтения SuperAgent теперь регистрирует отдельный
шаг `started → success/failed` в SQLite. Хранятся только имя инструмента,
номер попытки/шага, отметки времени, квитанция, SHA-256 аргументов и
результата. Исходные параметры запроса, содержимое ответа, пользовательские
сообщения и секреты в журнале **не дублируются**.

После аварийного завершения незаконченные шаги помечаются
`interrupted`, а задание возвращается в очередь. При новом назначении
безопасные read-only инструменты могут выполняться заново, но повтор одного
и того же шага в рамках одной попытки не допускается.

Команда `/agent status <id>` отображает последнее действие из журнала
только владельцу задания. Неправильный JSON-отчёт или пустой результат LLM
больше не переводит автономное задание в `ready`.

**Граница этапа:** это журналирование read-only шагов, а не подтверждение
изменений ОС и не exactly-once запись во внешние сервисы. В дальнейшем
изменяющие операции потребуют отдельных idempotency keys, approval gate,
проверки конечного состояния и правил отката. Создание дополнительной
таблицы в локальной SQLite-базе выполняется только при обновлении Лешего;
существующие таблицы и данные не удаляются.

Локальная проверка владельцем: `python -m unittest tests.test_cognitive_journal -v`.
В GitHub сборки и тесты не запускаются.

## Этап 4 (1.10.43): подтверждаемое создание документов

При прямом поручении «создай файл/отчёт/документ» SuperAgent может
подготовить Markdown-артефакт `artifact.propose`. Эта операция
**не создаёт файл**: текст помещается в отдельную запись SQLite с
уникальным идентификатором `ART-...`, привязкой к владельцу и заданию.

Владельцу доступны команды:

- `/agent preview ART-...` — показать весь текст и SHA-256;
- `/agent approve ART-...` — однократно создать файл;
- `/agent reject ART-...` — отказать в записи.

Файл появляется только после подтверждения в
`LeshyBrain/workspace/cognitive-artifacts/<хеш-владельца>/ART-....md`
(либо в настроенном `workspace_root`). Имя формирует сервер:
модель не выбирает абсолютные пути. Используется эксклюзивное
создание без перезаписи и проверка SHA-256 прочитанного файла. При
сбое записи артефакт помечается `failed` и не повторяется
автоматически. Подтверждение действует 24 часа.

Команды проверяют владельца задания; на этом этапе модель
не может запускать shell, изменять существующие файлы, управлять
покупками или самостоятельно утверждать создание документа.
Файлы не удаляются при откате версии. Схема базы расширяется
только новой таблицей `superagent_artifacts`.

Известное ограничение: это **только** создание нового Markdown-файла,
а не универсальный файловый агент. Локальная проверка:
`python -m unittest tests.test_cognitive_artifacts -v`.

## Этап 5 (1.10.45): восстановление после прерванного подтверждения

При запуске выполняется сверка записей `applying` с фактическими
файлами **только чтением**, без автоматического создания и удаления:

- Если файл существует и SHA-256 совпадает, документ помечается
  `applied`, а ожидавшая подтверждения задача — `ready`.
- Если файл отсутствует, повреждён или недоступен, документ получает
  статус `failed`, а задача — `blocked`. Частичный файл сохраняется
  для ручной диагностики и **не перезаписывается**.
- Если документ уже отмечен `applied`, но задача осталась в `waiting`,
  статус согласуется с проверенным файлом.
- Истёкшие, ещё не подтверждённые предложения получают `expired`.

После проверки агент отображает статус владельцу и сообщает результат
в прежнем чате, если сохранена сессия. Сама сверка не делает никаких
внешних запросов и не запускает платные сервисы.

Этап рассчитан на **один запущенный экземпляр** SuperAgent на одну
SQLite-базу. Одновременная работа нескольких процессов с одной базой
требует отдельной межпроцессной блокировки. Текущие функции не дают
общего права изменять файлы или исполнять команды.

Локальные сценарии проверки:
`python -m unittest tests.test_cognitive_artifacts tests.test_cognitive_journal -v`.
Они включают сохранённый файл, частичный файл, отсутствие файла,
пропущенную запись в БД и истечение срока разрешения.

## Этап 6 (1.10.46): межпроцессное лидерство SuperAgent

При открытии одной SQLite-базы несколько экземпляров приложения теперь
соревнуются за неблокирующий файловый lock `leshy.sqlite3.superagent.lock`.
Один процесс становится активным исполнителем; остальные остаются
наблюдателями и периодически проверяют освобождение lock.

**Важное исправление:** создание второго экземпляра больше не приводит
к сбросу `working` в `queued`, если первый исполнитель жив.
Восстановление прерванных заданий и сверка артефактов выполняются
только владельцем блокировки. После аварийного завершения процесса
ОС освобождает lock, следующий экземпляр восстанавливает состояние.

Кнопки подтверждения и отклонения файловых артефактов также исполняются
только активным экземпляром. В остальных экземплярах возвращается
понятная ошибка, но запись не выполняется.

Ограничения: блокировка работает для нескольких процессов **на одном
локальном хранилище**. Для сетевой ФС, репликации SQLite и распределённого
кластера нужен отдельный coordinator. Прервать уже работающую LLM
мгновенно механизм не может: блокировка удерживается до выхода worker,
а приложение ждёт его завершения при остановке. Модифицировать или
удалять lock-файл вручную нельзя; он должен сохраняться после остановки.

Локальная проверка: `python -m unittest tests.test_superagent_leadership
tests.test_cognitive_artifacts tests.test_cognitive_journal -v`.
GitHub Actions не запускаются.

## Этап 7 (1.10.47): исключение повторного выполнения

При перезапуске, если предложение документа успело сохраниться в SQLite,
а исходная задача осталась `working` (позже восстановлена как `queued`),
SuperAgent возвращает её в `waiting` с **тем же** `ART-ID`.
Новая генерация документа, дублирование файла или автоматическая запись
не допускаются. Команды `/agent retry` и `/agent answer` не обходят
незавершённое подтверждение.

Существующие состояния `applying`, `applied` и `failed` сверяются
по SHA-256, если задача после сбоя осталась `queued` или `waiting`.
Подтверждение эффекта выполняется только чтением файла. Оставшиеся после
сбоя недоставленные отчёты в SQLite отправляются после захвата
межпроцессной блокировки без повторного вызова модели/инструмента.

В тестах добавлено реальное аварийное завершение отдельного временного
Python-процесса, удерживающего lock, и проверка повторного захвата
после `kill`. Этот тест не трогает запущенного Лешего пользователя
и выполняется только при локальном вызове набора тестов.

Локальная проверка:
`python -m unittest tests.test_superagent_leadership tests.test_cognitive_artifacts -v`.
GitHub Actions не запускаются. Сохраняется ограничение локальной SQLite:
кластерный distributed lock и exactly-once доставка сообщений не реализованы.

## Этап 8 (1.10.48): проверка результата и обратимый откат

Владелец может проверить состояние документа через
`/agent verify ART-ID`. При проверке учитываются текущие байты файла
и SHA-256, а не только сохранённый статус `applied`.

Новая команда `/agent rollback ART-ID` позволяет **явно** откатить
подтверждённый документ, сохранив его содержимое. Вместо удаления
нового файла модуль перемещает его в отдельный архив:
`workspace_root/cognitive-artifacts/.rollback/<хеш-владельца>/ART-ID.md`.
Перемещение возможно только если исходный файл существует, его хеш
совпадает с сохранённым и задачу завершил уполномоченный исполнитель.
Это **не автоматический** откат: модель не получает права вызывать
команду самостоятельно. Архив сохраняет файл для ручного восстановления.

Перемещение использует безопасное создание жёсткой ссылки без
перезаписи архивного имени и удаление исходного имени после проверки
содержимого и идентичности файла. Операция выполняется на одном локальном
томе. При сбое система не удаляет архив и не перезаписывает исходник.
На следующем запуске только читает оба пути и сверяет SHA-256:
архив подтверждён и исходника нет → `archived`; в противном случае
`failed` и требуется ручная проверка. Для случая `archived` повтор
команды идемпотентен при неизменном хеше.

`/agent retry` и `/agent answer` больше не перезапускают задание,
если с ним уже связан любой документ, независимо от статуса
`pending`, `failed`, `rejected` или `applied`. Новая попытка
создания документа требует **нового задания**.

Ограничения: откат действует только для Markdown-документов, созданных
в Cognitive Core и только на локальном томе, поддерживающем жёсткие ссылки.
Это не откат произвольных изменений системы, сторонних приложений и не
восстановление старых файлов. Тесты добавлены, но должны быть выполнены
в локальном окружении до использования механизма.

Локальные сценарии:
`python -m unittest tests.test_cognitive_rollback -v`.

## Дополнительная защита Computer Use (1.10.53)

Контроллер рабочего стола теперь не может запускаться без явно указанного permission_check — ранее самостоятельный экземпляр ComputerUseController по умолчанию разрешал управление. Встроенный OS Controller остаётся запрещённым по умолчанию. Подключение пользовательского Computer Use к общему разрешению ОС требуется проверять на каждом шаге; в случае отзыва прав выполнение прекращается до следующего ввода.

Команды из PowerShell отслеживаются по процессам, но дочерние процессы, способные отделиться от дерева или запуститься через системные службы, могут потребовать дополнительных OS-level ограничений. Поэтому абсолютно гарантировать завершение любых сторонних процессов из произвольного скрипта нельзя. Сценарии тестирования написаны, но на пользовательском оборудовании ещё не проверены.

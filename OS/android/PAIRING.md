# Привязка Android-клиента к серверу — проект протокола v1

**Статус:** только клиентская заготовка. Серверный endpoint привязки в текущем API не найден; это НЕ действующая регистрация, авторизация или вход владельца. `GET /v1/status` остаётся самостоятельной диагностикой.

## Уже внесено в клиент
- `DeviceIdentity.kt` генерирует локально по явному нажатию EC P-256 ключ подписи `SHA256withECDSA` в `AndroidKeyStore`; приватный ключ не экспортируется обычным API Android. Аппаратная защита **не гарантируется**: зависит от устройства.
- Публичный ключ экспортируется как X.509 SPKI в base64url без padding, отпечаток — SHA-256 от **байтов DER SPKI** в шестнадцатеричном нижнем регистре (64 символа). В UI показывается только отпечаток, не приватный ключ.
- Метод `signPairingChallenge` пока **не вызывается**. Он подписывает байты ASCII `leshy-satellite-pair-v1\u0000` плюс ровно 32 байта запроса (ECDSA, DER-подпись). Не использовать эту подпись как самостоятельный токен.
- Кнопка удаления уничтожает только локальный ключ. Когда серверное pairing появится, нужен отдельный защищённый запрос отзыва доступа на сервере.

## Обязательное серверное расширение (НЕ реализовано)
1. Владелец после **подтверждённой авторизации на сервере** создаёт короткоживущий, одноразовый запрос на привязку с разрешениями для клиента. Нельзя принимать `owner_id` или роль «создатель» со слов Android-клиента.
2. Android получает запрос через штатное TLS-соединение с проверкой сертификата; передаёт публичный ключ. Никаких секретов в URL, глубоких ссылках и логах.
3. Сервер выдаёт случайный криптографический 32-байтный challenge, связанный с конкретным запросом, пользователем и ключом. Проверяет срок действия, однократность, защиту от replay, лимит попыток и подтверждение владельца.
4. Клиент подписывает challenge указанным выше разделённым по контексту форматом; сервер проверяет подпись по **переданному публичному ключу**, а затем выдаёт только отзываемый и ограниченный по полномочиям доступ **конкретному устройству**. Отпечаток сам по себе НЕ доказывает право доступа.
5. Отдельные методы сервера: статус привязки, отзыв доступа, истечение сроков, аудит без секретов, миграция ключа. При удалении локального ключа доступ на сервере должен быть отозван отдельно; после утери устройства владелец отзывает его с другого доверенного клиента.
6. Голос, фото и данные лиц запрещено передавать до отдельного согласия, готового авторизованного канала и ограничения прав. Одна биометрия не заменяет owner confirmation для опасных команд.

**Не делать:** копировать общий `LESHY_API_TOKEN` в Android, обходить проверки TLS, выставлять гостю права создателя, выдавать успешный `/v1/status` за авторизацию.

## Проверки перед выпуском
- Корректность ECDSA и отпечатка на настоящем Android, поддержка Keystore на целевых прошивках, случай отозванного или недоступного ключа, сброс и переустановка.
- Серверные тесты: подмена ключа, повтор challenge, просроченный challenge, неавторизованный запрос, revoke, потеря сети и конкурентные попытки pairing.
- CI, сборки и Android E2E **не запускались** в связи с действующими ограничениями репозитория до 01.12.2026. Независимое ревью обязательно; PR остаётся draft.
